# TeamFlow Sports

Telegram-бот и Telegram Mini App для управления спортивными командами (баскетбол, футбол, волейбол, хоккей и другие командные виды спорта).

Статус: **Итерация 11 из 15** — конфигурация, PostgreSQL, авторизация через Telegram Mini App `initData`, профили игрока/тренера, команды с ролями/приглашениями/заявками, загрузка файлов на Яндекс.Диск, личная библиотека упражнений/планов/шаблонов заданий, собственная светлая дизайн-система, тренировки и посещаемость, самостоятельные тренировки с отчётами, задания игрокам с гибкой адресацией и отчётами, матчи с составом и итогом, календарь и уведомления с фоновой `asyncio`-задачей, статистика команды и игрока с универсальной системой показателей. Подробный план всех итераций — в конце файла.

## Архитектура

```
SportHelper/
  backend/            FastAPI + aiogram 3 (Python 3.12)
    app/
      config.py         конфигурация из .env
      database.py        пул asyncpg + раннер миграций (schema.sql + patches)
      security/           проверка Telegram initData, JWT
      integrations/         клиент REST API Яндекс.Диска
      services/               переиспользуемые сервисы (потоковая загрузка файлов)
      repositories/        SQL-запросы к БД
      schemas/              Pydantic-модели запросов/ответов
      api/routes/            HTTP-роуты FastAPI
      bot/                    обработчики aiogram
      main.py                 точка входа FastAPI (uvicorn app.main:app)
    run_bot.py            точка входа Telegram-бота (long polling)
    scripts/               dev-утилиты (например, генератор тестового initData)
    tests/                pytest
  frontend/            Telegram Mini App (React + TypeScript + Vite)
  database/
    schema.sql          схема для чистой базы
    patches/             последовательные SQL-патчи для существующей базы
  docs/
    configuration.md    подробное описание всех переменных .env
  .env.example          пример конфигурации
```

Backend и бот — это два независимых процесса одного кодового пути: FastAPI-сервер отвечает на HTTP-запросы Mini App, бот обрабатывает команды в Telegram (`/start` и, начиная с итерации 13, административные команды).

## Требования

- **Python 3.12** (в системе может быть несколько версий — используйте `py -3.12`)
- **Node.js 20+** и npm
- **PostgreSQL 14+**, запущенный локально или доступный по сети
- Telegram-бот, созданный через [@BotFather](https://t.me/BotFather) (нужен токен)

## Установка и запуск (пошагово, для новичка)

Все команды приведены для PowerShell на Windows. Пути указаны от корня репозитория.

### 1. Backend: виртуальное окружение и зависимости

```powershell
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\pip install --upgrade pip
.\.venv\Scripts\pip install -r requirements.txt
```

### 2. PostgreSQL: роль и база данных

Откройте `psql` (или pgAdmin) под суперпользователем (обычно `postgres`) и выполните:

```sql
CREATE ROLE teamflow LOGIN PASSWORD 'придумайте-пароль';
CREATE DATABASE teamflow_sandbox OWNER teamflow;
```

Таблицы создавать вручную не нужно — backend сам применит `database/schema.sql` при первом запуске (см. `app/database.py`).

### 3. Файл `.env`

В корне репозитория:

```powershell
Copy-Item .env.example .env
```

Откройте `.env` и заполните как минимум:

```dotenv
TELEGRAM_BOT_TOKEN=токен_от_BotFather
TELEGRAM_BOT_USERNAME=username_бота_без_@
MINI_APP_URL=http://localhost:5173
DATABASE_URL=postgresql://teamflow:придумайте-пароль@127.0.0.1:5432/teamflow_sandbox
JWT_SECRET=любая-длинная-случайная-строка
CORS_ORIGINS=http://localhost:5173
```

`TELEGRAM_BOT_USERNAME` нужен для ссылок-приглашений в команду (итерация 3) — без него ссылка упадёт назад на прямой адрес Mini App вместо `t.me/...`.

Для загрузки логотипа команды (итерация 4) нужен OAuth-токен Яндекс.Диска — как его получить, см. [docs/configuration.md](docs/configuration.md#яндексдиск-с-итерации-4). Без токена сама Mini App и все функции без файлов работают как обычно — загрузка логотипа просто вернёт понятную ошибку `503 yandex_disk_not_configured`.

```dotenv
YANDEX_DISK_OAUTH_TOKEN=токен_технического_аккаунта
YANDEX_DISK_ROOT_FOLDER=/TeamFlow
```

Подробности по каждому параметру — в [docs/configuration.md](docs/configuration.md). Файл `.env` никогда не коммитится в git.

### 4. Запуск backend (API)

```powershell
cd backend
.\.venv\Scripts\python -m uvicorn app.main:app --reload
```

При старте backend автоматически применит миграции к базе данных и (начиная с итерации 10, если задан `TELEGRAM_BOT_TOKEN`) запустит единственную фоновую `asyncio`-задачу — отправку уведомлений, простановку просроченных заданий и очистку файлов с истёкшим сроком мягкого удаления; отдельного процесса для неё не нужно, она живёт внутри процесса backend и завершается вместе с ним. Проверить, что всё работает:

- http://localhost:8000/api/health — статус backend и БД
- http://localhost:8000/docs — интерактивная Swagger-документация API

### 5. Запуск Telegram-бота

В отдельном терминале:

```powershell
cd backend
.\.venv\Scripts\python run_bot.py
```

Напишите боту `/start` в Telegram — он пришлёт кнопку для открытия Mini App.

Бот работает как отдельный процесс от backend и (начиная с итерации 13) держит собственный пул подключений к той же базе — при старте он тоже применяет миграции, поэтому необязательно сначала поднимать backend. Если ваш Telegram ID указан в `ADMIN_TELEGRAM_IDS`, вам станут доступны административные команды — напишите `/admin`, чтобы увидеть список.

### 6. Запуск frontend (Mini App)

В ещё одном терминале:

```powershell
cd frontend
npm install
npm run dev
```

Frontend поднимется на http://localhost:5173. Открытый напрямую в браузере (не из Telegram), он покажет экран «Откройте приложение через Telegram» — это ожидаемое поведение: `initData` доступен только внутри настоящего Telegram-клиента.

Чтобы протестировать Mini App по-настоящему, Telegram должен открыть **HTTPS**-адрес. Для локальной разработки удобно поднять туннель (например, `ngrok http 5173`, авторизация через `ngrok config add-authtoken ...`; либо `cloudflared tunnel --url http://localhost:5173 --protocol http2`, если UDP/QUIC блокируется сетью) и указать выданный HTTPS-адрес в `MINI_APP_URL` в `.env`.

Frontend по умолчанию принимает запросы только с известных хостов (защита Vite от DNS rebinding) — домены `*.ngrok-free.dev`, `*.ngrok-free.app` и `*.trycloudflare.com` уже разрешены в `frontend/vite.config.ts` (`server.allowedHosts`).

**Важно:** бесплатные туннели выдают новый домен при каждом перезапуске. После перезапуска туннеля обновите и `MINI_APP_URL`, и `CORS_ORIGINS` в `.env`, затем перезапустите backend и бота (настройки читаются один раз при старте процесса).

Для ручной проверки backend-эндпоинтов без реального Telegram (например, через Swagger `/docs`) есть dev-скрипт, который генерирует валидно подписанный `initData` по токену бота из `.env`:

```powershell
cd backend
.\.venv\Scripts\python scripts\dev_init_data.py --user-id 555 --first-name Иван --username ivanov
```

В Swagger UI роуты, требующие авторизации, используют схему HTTP Bearer — нажмите **Authorize** и вставьте `access_token`, полученный от `POST /api/auth/telegram`, без слова `Bearer`.

### 7. Песочница и основной бот

Проект поддерживает два независимых инстанса — `sandbox` (для проверки обновлений) и `main` (боевой), с разными токенами бота, базами и `.env`-файлами:

```powershell
$env:ENV_FILE = ".env.sandbox"; .\.venv\Scripts\python -m uvicorn app.main:app --port 8000
$env:ENV_FILE = ".env.main";    .\.venv\Scripts\python -m uvicorn app.main:app --port 8001
```

Так же указывается `ENV_FILE` для `run_bot.py`. Подробнее — в [docs/configuration.md](docs/configuration.md).

## Тесты

```powershell
cd backend
.\.venv\Scripts\python -m pytest
```

С отчётом о покрытии (`pytest-cov`, добавлен в итерации 15):

```powershell
.\.venv\Scripts\python -m pytest --cov=app --cov-report=term-missing
```

Тесты проверяют подпись Telegram `initData`, маршруты авторизации и профилей, маршруты команд (создание, роли, лимит участников, единственность капитана/основного тренера, права на управление ассистентами и снятие с ролей, приглашения, заявки, блокировки, передача роли, команда без тренера), задания (создание по всем типам адресации, обязательные поля отчёта, повторная отправка, старт/двойной старт, валидация чужого плана/упражнения при редактировании), загрузку/скачивание файлов (права доступа, проверка MIME-типа и размера), библиотеку упражнений/планов (владение, видимость для команд, состав плана, дублирование), ИИ-функции (черновики, права доступа, обработка некорректного JSON от модели) и rate limiter — без обращения к реальной БД, реальному Яндекс.Диску или реальному Yandex AI Studio (репозитории, `YandexDiskClient` и `YandexAIClient` подменяются тестовыми двойниками в `tests/conftest.py`). Ограничения на уровне PostgreSQL (частичные уникальные индексы, триггер лимита в 50 человек), реальная интеграция с Яндекс.Диском (загрузка → скачивание, побайтовое сравнение) и реальные вызовы Yandex AI Studio дополнительно проверены вручную на реальной инфраструктуре при разработке каждой итерации.

Покрытие репозиториев (`app/repositories/*.py`) и интеграций (`app/integrations/*.py`, `app/database.py`) в отчёте `pytest-cov` намеренно низкое — это не пробел, а следствие архитектуры тестов: маршруты тестируются через FastAPI `TestClient` с подменёнными репозиториями (проверяется бизнес-логика и права доступа), а корректность самого SQL и реальных HTTP-интеграций проверяется вручную против настоящей инфраструктуры при каждой итерации (см. разделы «Реализовано в итерации N» выше) — так находятся баги, которые моки in-memory принципиально не могут поймать (несовпадение имён колонок, реальные ограничения БД, форма ответа внешнего API).

## Реализовано в итерации 1

- Конфигурация через `.env` (`pydantic-settings`), режимы `sandbox`/`main`.
- Пул подключений PostgreSQL (`asyncpg`) и автоматический раннер миграций: `database/schema.sql` для чистой базы + `database/patches/*.sql` для последующих версий, с таблицей `schema_versions`.
- Проверка подписи Telegram Mini App `initData` (HMAC-SHA256 по алгоритму Telegram) и проверка свежести `auth_date`.
- Выпуск и проверка собственного JWT (HTTP Bearer, с кнопкой Authorize в Swagger).
- `POST /api/auth/telegram` — вход/регистрация по `initData`, `GET /api/auth/me` — текущий пользователь.
- `GET /api/health` — проверка backend + БД.
- Бот на aiogram 3: команда `/start` с кнопкой открытия Mini App.
- Frontend: Vite + React + TypeScript + `@tma.js/sdk`, тёмная тема на CSS-переменных Telegram (`--tg-theme-*`), состояния loading/empty/error/forbidden, Error Boundary на случай непойманных ошибок рендера.
- Unit- и API-тесты (pytest), Swagger/OpenAPI.

## Реализовано в итерации 2

- Таблицы `player_profiles` и `coach_profiles` (1:1 с `users`, патч `database/patches/0002_profiles.sql`), поле `users.active_mode` для хранения текущего активного режима.
- `GET /api/profile/me` — текущие профили игрока/тренера и активный режим.
- `PUT /api/profile/player`, `PUT /api/profile/coach` — создание/редактирование профиля (upsert), с валидацией диапазонов (возраст, рост, вес, опыт) и фиксированным списком уровней.
- `POST /api/profile/active-mode` — переключение между режимами игрока и тренера; отклоняется (`409 profile_required`), если соответствующего профиля ещё нет. Первый созданный профиль активирует режим автоматически.
- Frontend: онбординг выбора роли, формы профиля игрока/тренера, карточка профиля с переключением режима и созданием второго профиля.

## Реализовано в итерации 3

- Таблицы `teams`, `team_members`, `team_invites`, `team_join_requests`, `team_blocks` (патч `database/patches/0003_teams.sql`); частичные уникальные индексы на «один основной тренер» и «один капитан» на команду; триггер лимита в 50 участников.
- Роли: основной тренер, помощник тренера, капитан, игрок — все переходы прав проверяются backend (кто может назначать капитана/помощника, удалять, блокировать, создавать приглашения).
- `POST /api/teams`, `GET /api/teams/mine`, `GET/PUT /api/teams/{id}` — создание и управление командой (создание требует заполненного профиля тренера).
- `GET /api/teams/{id}/members`, `PATCH/DELETE .../members/{user_id}`, `POST .../members/{user_id}/block` — состав, назначение ролей, удаление, блокировка повторного вступления (только основной тренер).
- `POST /api/teams/{id}/leave` — выход из команды для любой роли; если уходит основной тренер, команда получает статус «без тренера».
- `POST /api/teams/{id}/transfer-ownership` — передача роли основного тренера с обязательной точной фразой-подтверждением.
- Приглашения по ссылке (`POST/GET /api/teams/{id}/invites`, `GET/POST /api/invites/{token}[/apply]`): многоразовые, 24 часа, диплинк вида `t.me/<bot>?start=invite_<token>`; отдельный вид приглашения — капитан приглашает нового основного тренера для команды без тренера, принятие происходит без этапа заявки.
- Заявки на вступление (`GET /api/teams/{id}/applications`, `.../accept`, `.../reject`) — принимает основной тренер или помощник.
- Бот: `/start` с диплинком передаёт токен приглашения в Mini App через URL.
- Frontend: нижняя навигация «Команды/Профиль» для тренера, список и создание команд, карточка команды (обзор/состав/настройки), приглашения, заявки, модальные подтверждения для опасных действий (удаление, блокировка, выход, передача роли), раздел «Мои команды» в профиле игрока, экран принятия приглашения по ссылке.

## Реализовано в итерации 4

- Таблица `files` (владелец, команда, связанная сущность, путь на Диске, имя, MIME-тип, размер, статус, уровень доступа PRIVATE/TEAM/COACHES_ONLY) + `teams.logo_file_id` (патч `database/patches/0004_files.sql`).
- `app/integrations/yandex_disk.py` — асинхронный клиент REST API Яндекс.Диска (создание папок, получение upload/download-ссылок, потоковая загрузка/скачивание). OAuth-токен используется только backend и никогда не логируется и не уходит на frontend.
- `POST /api/teams/{id}/logo` — потоковая загрузка логотипа (основной тренер/помощник), с проверкой MIME-типа и лимита размера файла без буферизации в память; повторная загрузка мягко удаляет предыдущий файл.
- `GET /api/files/{id}` — потоковая отдача файла через backend с проверкой уровня доступа (для логотипа — любой участник команды).
- Frontend: загрузка логотипа в настройках команды, отображение через авторизованный запрос с blob-URL (`<img>` не может слать заголовок Authorization напрямую).
- 6 новых тестов с фейковым клиентом Яндекс.Диска; полный цикл (загрузка → скачивание, побайтовое сравнение) дополнительно проверен на реальном Яндекс.Диске.

## Реализовано в итерации 5

- Таблицы `exercises`, `exercise_team_shares`, `training_plans`, `training_plan_exercises` (патч `database/patches/0005_exercises.sql`); soft delete на упражнениях и планах.
- Модель: упражнения и планы — личная библиотека тренера (не привязаны к конкретной команде), переиспользуются во всех его командах. Упражнение можно «показать» команде — участники видят его как необязательный материал, только для чтения; изменять/удалять может только владелец.
- `app/services/uploads.py` — общая потоковая загрузка на Яндекс.Диск, вынесена из `files.py`, переиспользуется для логотипа команды и фото/видео упражнений.
- `POST/GET/PUT/DELETE /api/exercises`, `.../photo`, `.../video`, `.../share`, `.../share/{team_id}`, `GET /api/teams/{id}/exercises` — CRUD упражнения, загрузка медиа, управление видимостью для команд.
- `POST/GET/PUT/DELETE /api/plans`, `.../duplicate`, `.../exercises` — план как переиспользуемый шаблон с 4 секциями (разминка/основная/игровая/заминка), каждое упражнение в плане может переопределять подходы/повторения/длительность/отдых под конкретный план; дублирование копирует весь список упражнений.
- Frontend: вкладка «Библиотека» у тренера (Упражнения/Планы), формы создания/редактирования, загрузка фото и видео (просмотр через авторизованный blob-URL/`<video>`), конструктор плана по секциям с выбором упражнения и параметров, вкладка «Упражнения» внутри команды (только чтение для всех участников).
- 11 новых тестов; реальная сквозная проверка на живой инфраструктуре: создание упражнения, загрузка фото на Яндекс.Диск и скачивание с побайтовым сравнением, создание плана, добавление упражнения в план, дублирование плана, показ упражнения команде.

## Доработки после итерации 5 (по обратной связи, перед итерацией 6)

- Игрок теперь может открыть карточку команды (обзор, состав, показанные упражнения/планы) — раньше список команд был только для просмотра и выхода.
- Тренер и помощник могут открыть профиль игрока из состава команды: `GET /api/teams/{id}/members/{user_id}/profile` (доступ только тренерскому составу).
- Планы тренировок теперь можно «показать» команде — таблица `training_plan_team_shares` (патч `0006_plan_shares.sql`), симметрично упражнениям; вкладка «Планы» появилась и внутри команды.
- Формы отмечают обязательные поля звёздочкой и подсказкой.
- Фото упражнения отображается крупно (как видео), а не мелким квадратом — это может быть схема, важны детали.
- Список упражнений и планов — с поиском по названию/виду спорта; кликабельные карточки везде получили визуальную стрелку.

**Багфиксы (после первого прогона доработок):**

- Фото/видео упражнения возвращали `403` игрокам команды, которой упражнение было показано — файл сохраняется как `PRIVATE` (упражнение может быть показано сразу нескольким командам, поэтому у файла нет единственного `team_id`), но проверка доступа не учитывала это. `GET /api/files/{id}` теперь для `entity_type` `exercise_photo`/`exercise_video` дополнительно проверяет, показано ли упражнение команде, в которой состоит запрашивающий.
- Обрыв сети при обращении к Яндекс.Диску во время скачивания файла (`httpx.ConnectError` и подобные) не оборачивался в понятную ошибку и ронял ASGI-приложение необработанным исключением. `YandexDiskClient` теперь перехватывает `httpx.HTTPError` во всех методах и превращает их в `YandexDiskError`, которую роуты уже корректно обрабатывают.
- Добавлен регрессионный тест на видимость медиа упражнения для участника команды; исправление проверено на реальном Яндекс.Диске (загрузка → показ команде → скачивание игроком, побайтовое сравнение).

- **«Предложить тренировку (ИИ)» подстраивается под новый конструктор**: черновик личной тренировки от ИИ переделан со свободного текста на структурированный список упражнений — `POST /api/ai/personal-training-draft` принимает `style` («на повторения» / «круговая») и возвращает список `{exercise, reps, sets, duration_seconds}` вместо `description`; фронтенд заполняет ими строки конструктора, а не текстовое поле, дальше их можно редактировать как обычно.
- **Ревью найденных при этой доработке проблем** (независимый повторный проход по свежему коду — не по исходному запросу пользователя): отзыв о тренировке и ИИ-оценку теперь нельзя запросить для тренировки со статусом не «Проведена» напрямую через API (раньше это ограничивал только фронтенд — бэкенд принимал запрос всегда); ошибка загрузки отзыва о тренировке теперь показывается в интерфейсе с кнопкой «Повторить» вместо тихого исчезновения всего блока; ИИ-черновик личной тренировки, в котором модель не смогла вернуть ни одного валидного упражнения, теперь возвращает понятную ошибку вместо пустого «успешного» списка; запрос короткой (менее 10 минут) тренировки к ИИ-черновику теперь ограничивается на фронтенде до отправки, а не падает с общей ошибкой сервера; посещаемость игрока для ИИ-оценки тренировки теперь запрашивается одной строкой вместо всего состава команды.
- Реальная сквозная проверка на живой инфраструктуре: уведомления о новой тренировке/матче/задании долетают до всех участников команды, кроме автора; отзыв и ИИ-оценка отклоняются до отметки «Проведена» и проходят после; посторонний получает `403`, а не `409`, даже если тренировка не завершена (порядок проверок); черновик личной тренировки от ИИ в обоих стилях («на повторения» и «круговая») возвращает нужную структуру; rate limiter — 61-й запрос за минуту от одного пользователя получает `429`, второй пользователь с того же IP не задет.
