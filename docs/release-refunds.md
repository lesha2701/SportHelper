Старые версии приложений не ломаются: они не знают `can_cancel` и `cancellation`, а статус `cancelled` и раньше был допустим. Отменить запись
из старой версии нельзя, видна она как отменённая.

## A. Проверить прод (один раз, на сервере, в `/opt/sporthelper`)

- [ ] Миграция применилась: `docker compose logs backend | grep 0043` → строка `Applying patch 0043_booking_cancellations.sql (version 43)`
      (или `docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c '\d booking_cancellations'`).
- [ ] Маршруты на месте: `curl -s -o /dev/null -w "%{http_code}\n" https://<домен>/api/bookings/00000000-0000-0000-0000-000000000000/cancel-preview`
      → `401` (без входа). `404` значит, что работает старый код.
- [ ] В `.env` строка `CANCEL_FREE_HOURS` либо отсутствует (тогда 24 ч), либо равна согласованному значению. Печатать `.env` целиком не нужно:
      `grep -c '^CANCEL_FREE_HOURS=' .env`.
- [ ] В кабинете ЮKassa у HTTP-уведомлений включено событие **`refund.succeeded`** (вместе с `payment.succeeded`, `payment.canceled`,
      `payment.waiting_for_capture`). Без него возврат всё равно дойдёт, но через сверку, то есть через минуты, а не сразу.
- [ ] Получатели инцидентов настроены (`FINANCE_ADMIN_EMAILS`): им приходит уведомление «Финансовый инцидент» в приложении; отказ ЮKassa
      в возврате теперь тоже его создаёт (REF-19).

Реальными деньгами отмену на проде не проверяем. Достаточно отменить **неоплаченную** подтверждённую запись своей тестовой парой
«тренер — игрок»: она уходит в «Отменённые», второй стороне приходит уведомление, денежных строк нет.

## B. Что смотреть первые дни

```sql
-- возвраты, которые не дошли до конца больше чем за час (норма — пусто)
SELECT id, status, amount_kopecks, created_at, failure_reason FROM refunds
 WHERE status IN ('requested', 'pending') AND created_at < now() - interval '1 hour';

-- открытые инциденты по возвратам (refund_failed — вернуть вручную в админке «Финансы»)
SELECT kind, payment_id, detail, created_at FROM payment_incidents WHERE status = 'open' AND kind LIKE 'refund%';

-- как отменяют: кто, по какому правилу, сколько вернули
SELECT cancelled_by_role, policy, count(*), sum(refund_kopecks) / 100 AS rub FROM booking_cancellations GROUP BY 1, 2;
```

В логах: `grep "stays queued"` — возврат не ушёл сразу и ждёт сверки (это не ошибка, если потом исчезает из первого запроса).

## C. Если ЮKassa отказала в возврате

Отмена при этом уже прошла, резерв в платеже снят, у игрока на карточке «Банк не принял возврат…», финансовым администраторам пришёл инцидент
`refund_failed`. Деньги тренеру сами не уйдут: начисление отменённой записи не выпускается автоматически (нет подтверждённого занятия).
Администратор делает возврат вручную: админ-панель → «Финансы» → платёж → «Вернуть деньги игроку», затем закрывает инцидент.

## D. Откат

Миграция `0043` только добавляет таблицу `booking_cancellations`, ничего не меняет и не удаляет — откат кода её не требует трогать.
После отката старый код:
- не даёт отменять записи (маршрутов нет), уже отменённые остаются `cancelled`;
- досылает возвраты, стоящие в очереди, той же сверкой (машина возвратов была и раньше).

Порядок отката — общий: [`rollback.md`](rollback.md).
