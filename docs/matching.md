# Подбор тренера

Проект и решения: [docs/superpowers/specs/2026-11-23-coach-matching-design.md](superpowers/specs/2026-11-23-coach-matching-design.md).
Сейчас работают **этапы 1 и 2**: анкета и очередь заявок; согласие тренера на подбор, предложения тренерам, их ответы и выбор
спортсмена. Повышенная комиссия за первую тренировку, обязательная оплата и открытие контактов — этап 3 (пока не работают: первая
запись идёт по обычным правилам).

## Анкета («Тренеры» → «Подобрать тренера»)
Только вошедший человек. Обязателен вид спорта (2–100 символов); остальное по желанию: цель (до 1000), уровень
(`beginner|amateur|advanced|pro`), формат (`online|offline|any`), город, бюджет за занятие «от» и «до» (число, `от ≤ до`), дни недели
(`0` = понедельник … `6` = воскресенье, как в окнах тренера), время суток (`morning|day|evening`), уточнение по времени (до 500),
комментарий (до 1500). Возраста и других данных, которых нет на платформе, в анкете нет (среди спортсменов бывают дети).

Ограничения: 5 заявок в час и не более 3 незакрытых заявок одновременно (`409 too_many_open`). Заявки удаляются вместе с данными
человека при удалении аккаунта.

## API человека
* `POST /api/match-requests` — отправить анкету (201).
* `GET /api/match-requests/mine` — свои заявки: поля анкеты и статус.
* `POST /api/match-requests/{id}/cancel` — отозвать открытую заявку (чужую — 404, уже обработанную — `409 bad_transition`).

Статус для человека: `new` «Отправлена», `in_progress` «Подбираем тренера», `matched` «Тренер выбран», `closed` «Обработана»,
`canceled` «Отозвана».
Внутренняя запись администратора человеку не показывается.

## Админка («Подбор тренера»)
Очередь: сверху открытые заявки, дольше всех ждущая — первой; затем обработанные. Поиск по спорту, городу, цели, автору (email, имя, ID).
Заявку берут в работу (`POST /api/admin/match-requests/{id}/take`, `new` → `in_progress`) и закрывают с записью об итоге
(`POST .../{id}/close`, `{note}`). Оба действия в журнале аудита: `match_request_take`, `match_request_close`. Список и просмотр —
`GET /api/admin/match-requests[/{id}]`. В меню рядом с разделом — число новых заявок.

Миграция: `database/patches/0056_coach_match_requests.sql`.

## Этап 2: тренер, предложения, ответы
**Согласие тренера** (`/api/match-offers/settings`, только с профилем тренера, иначе `409 coach_profile_required`).
`GET` — включено ли, принятая и текущая версия условий, процент первой тренировки и сами условия (абзацы). `PUT {enabled,
accept_terms_version}` — включить можно только с текущей версией (`409 terms_required`); версия и время согласия сохраняются
(`coach_profiles.accepts_match_offers`, `match_terms_version`, `match_terms_accepted_at`). Новая редакция условий
(`TERMS_VERSION` в `services/match_offers.py`) выключает подбор у тех, кто не принял её заново. Выключить можно в любой момент.

**Предложение** (`coach_match_offers`): заявка + тренер, статусы `proposed → coach_accepted | coach_declined`, затем
`athlete_accepted | athlete_declined`, либо `withdrawn`; просроченное читается как `expired` (хранится прежний статус, фоновой задачи
нет). В предложении фиксируются процент первой тренировки (`MATCH_FIRST_SESSION_COMMISSION_PERCENT`, по умолчанию 50) и версия
условий; сроки: тренер отвечает `MATCH_COACH_REPLY_HOURS` (48), спортсмен — `MATCH_ATHLETE_REPLY_HOURS` (72).

**Кому можно предложить:** тренер включил подбор с текущими условиями; не автор заявки; не удалён и не заблокирован администраторами;
есть опубликованное и не скрытое модерацией объявление; нет блокировки в любую сторону; нет брони (ожидает/подтверждена) и нет
команды, где тренер ведёт спортсмена. Не больше 5 ожидающих ответа предложений на заявку; одному тренеру одну заявку — один раз.

### API тренера
* `GET /api/match-offers/incoming` — свои предложения (ожидающие сверху): анкета **без имени и контактов** (телефоны, почты, ссылки и
  @ники в свободном тексте заменяются на «[контакт скрыт]»), процент первой тренировки, срок ответа, сообщение администратора.
* `POST /api/match-offers/{id}/accept` — принять (повторно проверяются согласие и условия, блокировки; остальные ожидающие предложения
  заявки закрываются: кто принял первым — тот). Чужое — 404, уже закрытое — `409 offer_closed`, нельзя принять — `409 not_available`.
* `POST /api/match-offers/{id}/decline {reason?}` — отказаться (причина видна администраторам). Отказаться можно и при выключенном подборе.
Уведомления: тренеру `match_offer` (новое предложение), спортсмену `match_offer_reply` (тренер согласился); служебные, без переключателя.

### API человека
`GET /api/match-requests/mine` теперь содержит `offers` — только тренеры, которые согласились (и выбранный): карточка тренера и его
опубликованные объявления, срок выбора. Процент комиссии спортсмену не показывается.
* `POST /api/match-requests/offers/{id}/accept` — выбрать тренера: заявка `matched`, остальные предложения закрываются; дальше
  спортсмен записывается на тренировку в профиле тренера как обычно.
* `POST /api/match-requests/offers/{id}/decline` — отказаться от этого тренера: заявка остаётся в работе у администраторов.
Если заявку отозвали или закрыли, все ожидающие предложения закрываются сами.

### Админка
В карточке заявки — список предложений (ответ тренера, причина отказа, процент, сроки) и поиск подходящих тренеров:
`GET /api/admin/match-requests/{id}/candidates?q=` (тот же вид спорта, Pro и рейтинг — выше),
`POST .../{id}/offers {coach_user_id, message?}` (первая оферта берёт заявку в работу; `409 not_eligible | already_offered |
too_many_offers | bad_transition`), `POST /api/admin/match-requests/offers/{id}/withdraw`. В аудите: `match_offer_create`,
`match_offer_withdraw`. Закрыть можно и заявку со статусом `matched`.

Миграция: `database/patches/0057_coach_match_offers.sql` (колонки с значениями по умолчанию, одна таблица, два значения в CHECK
категорий уведомлений и статус `matched`; перед применением на боевой базе нужна резервная копия, как обычно).

### Для Android
Те же эндпоинты. Новые категории уведомлений `match_offer` (открыть «Подбор клиентов» тренера) и `match_offer_reply` (открыть вкладку
«Тренеры → Подобрать тренера»). Неизвестные категории и статусы предложений клиент должен показывать без падения.
