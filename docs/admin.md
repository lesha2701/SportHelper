# Админ-панель SportArenaGlobal

Панель живёт внутри сайта: `/admin` (раздел загружается отдельным куском кода и только для администратора). Всё, что она
показывает и делает, — настоящие данные PostgreSQL и настоящие операции; никаких заглушек. **Защита — только на сервере**:
интерфейс лишь повторяет то, что отвечает backend.

## Кто администратор

Подтверждённый (`email_verified_at`), не заблокированный и не удалённый аккаунт, чей email **точно** (без учёта регистра) есть в
`ADMIN_EMAILS` (через запятую). Правила:

* пробелы по краям убираются, пустые элементы игнорируются, регистр не важен;
* запись, не похожая на адрес (нет `@`, пробелы, `*`, `%` …), отбрасывается, а при старте в лог пишется предупреждение (без значений);
* никакого совпадения по домену, части адреса, имени пользователя или признаку с клиента; список пуст — доступа нет ни у кого;
* список читается при **каждом запросе** из конфигурации процесса: уберите адрес из `.env`, пересоздайте контейнер
  (`docker compose up -d --force-recreate backend`) — и доступ закрыт, аккаунт остаётся обычным;
* назначить себя администратором через API нельзя — такой возможности нет. Список администраторов никому не отдаётся:
  `/api/auth/me` говорит человеку только про него самого (`is_admin`).

## Вход и второй фактор

1. В «Аккаунт и безопасность» администратор включает TOTP (нужен пароль ещё раз) и получает 8 одноразовых резервных кодов.
   Секрет хранится зашифрованно, коды — хэшами. Включение и отключение 2FA попадают в журнал.
2. Каждая **новая сессия** снова требует код (или резервный код): настроенная 2FA сама ничего не открывает
   (`ADMIN_MFA_SESSION_HOURS`, по умолчанию 12 ч).
3. **Необратимые** действия (удалить файл из хранилища, удалить объявление) требуют кода не старше
   `ADMIN_SENSITIVE_MFA_MINUTES` (по умолчанию 10 мин): панель сама спросит код и повторит действие.
4. Любые изменения ограничены `ADMIN_WRITE_LIMIT_PER_MINUTE` (60/мин на администратора).

Потерян телефон — резервный код. Нет ни телефона, ни кодов — только администратор сервера: удалить строку из `user_mfa`
(`DELETE FROM user_mfa WHERE user_id = '…'`), после чего заново включить 2FA. Постоянных обходов нет.

Кто что может (проверяется тестом по **всем** маршрутам `/api/admin/*`):

| Вызывающий | Результат |
|---|---|
| без входа | 401 |
| обычный пользователь, в т. ч. с `isAdmin=true`, чужим email, заголовками, cookie, телом | 403 |
| администратор без 2FA / новая сессия без кода | 403 `mfa_setup_required` / `mfa_required` (кроме `GET /api/admin/session`) |
| администратор с кодом | доступ; изменения — ещё и CSRF-токен (cookie-сессия) |
| администратор, убранный из `ADMIN_EMAILS`, заблокированный или удалённый | 403 сразу |

Все ответы админ-API — `Cache-Control: no-store`.

## Разделы

| Раздел | Что делает |
|---|---|
| **Обзор** `/admin` | пользователи (всего / новые за день, 7, 30 дней / игроки / тренеры / заблокированные), DAU·WAU·MAU, тренировки (всего / активные / предстоящие / проведены), записи к тренерам, новые жалобы, контент в ожидании решения, 4 графика за 30 дней |
| **Пользователи** | поиск (email, имя, ID), фильтры роль/статус, сортировка по регистрации/активности, карточка, блокировка (срок или бессрочно, причина), снятие, история блокировок и мер |
| **Модерация** | фото и видео (аватары, логотипы, объявления, достижения, упражнения, отчёты): поиск по автору, связанный профиль/объявление, скрыть / восстановить / удалить |
| **Тренировки** | тренировки только для просмотра (участники, записи) + объявления тренеров: скрыть / вернуть / удалить |
| **Жалобы** | очередь со статусами «Новая / В работе / Решена / Отклонена», переход к объекту, решение с обязательным текстом |
| **Журнал** | кто, что, над чем, почему, результат, состояние до/после; фильтры; только чтение |

### Как считается активность (DAU / WAU / MAU)

* Таблица `user_activity_days`: одна строка на (пользователь, день по **UTC**). Анонимы не учитываются вовсе.
* Браузер шлёт «пульс» `POST /api/activity` при открытии приложения (сохранённый вход считается, пароль не нужен), затем
  не чаще раза в 5 минут и **только** если вкладка видима и человек что-то делал (клик, клавиша, прокрутка). Открытая
  и брошенная вкладка активной не считается; фоновые запросы (уведомления, проверка сессии) — тоже. Несколько вкладок и
  устройств сливаются в одну строку за день.
* Сервер дополнительно пишет в БД не чаще раза в 10 минут на пользователя (на процесс) — на запрос записей нет.
* DAU — отдельные люди за сегодня (UTC); WAU — за 7 дней, MAU — за 30 дней, включая сегодня. Удалённые аккаунты не считаются.
* История начинается с момента запуска учёта (на дашборде это написано); задним числом ничего не придумывается.

### Модерация контента

* **Скрыть** (первое и основное действие): файл перестаёт отдаваться всем (`/api/files/{id}` → 404, даже владельцу), пропадает
  из аватара, галереи и фото объявления. Модератор по-прежнему видит его через `/api/admin/media/{id}/content`. **Восстановить** возвращает.
* **Удалить** — необратимо, с галочкой и свежим кодом. Отказ, если файл связан больше чем с одним объектом, у другой записи тот же
  путь на диске или путь вне папки приложения (`<ROOT>/<режим>/…`). Порядок: БД (отсоединить от всего + запись в журнал,
  одна транзакция) → байты на Яндекс Диске → запись о файле. Диск недоступен — файл уже убран с сайта, фоновая очистка
  добавит. Публичных ссылок Яндекс Диска приложение не создаёт (файлы отдаются через backend), поэтому отзывать нечего.
* **Объявления**: скрытое модератором объявление уходит из каталога, поиска, профиля тренера и записи; уже оформленные записи
  остаются. Тренер не может вернуть его сам. Удалить можно, только если нет заявок и будущих записей (правило платформы).
  Объявления **заблокированного** тренера также не показываются, пока блокировка действует.
* **Тренировки** админ не изменяет — их ведут команды и тренеры.
* Блокировка пользователя завершает все его сессии сразу; остальной его контент остаётся, пока модератор не скроет его отдельно.
* Жалобы: `POST /api/complaints` (профиль, объявление, публичное фото/видео), не чаще 10 в час, одна открытая жалоба на объект
  от человека, на себя нельзя, видны только администраторам.

## Блокировки

`users.is_banned` — рубильник, который проверяет всё приложение; `banned_until` делает блокировку временной (истёкшая
перестаёт действовать **сразу** при чтении пользователя, фоновый цикл раз в 30 с лишь прибирает флаг и историю).
Нельзя заблокировать себя и другого администратора (его адрес убирают из `ADMIN_EMAILS` на сервере) — поэтому через панель
невозможно оставить сайт без администраторов. Удаление аккаунтов в панель не входит: используется существующий процесс
удаления самим пользователем (с отсрочкой).

## Миграции (применяются автоматически при старте backend)

| Патч | Что добавляет |
|---|---|
| `0035_user_activity.sql` | `user_activity_days`, `users.last_active_at` |
| `0036_user_bans_and_audit.sql` | `users.banned_until/ban_reason`, `user_bans`; `admin_audit_log.reason/result`, триггеры «только добавление» |
| `0037_moderation.sql` | `files.hidden_*`, `coach_listings.moderation_*`, `complaints` |

Все они только добавляют; существующие данные не меняются (кроме записи в `user_bans` для уже заблокированных и заполнения
`last_active_at` из сессий).

## Аудит

`admin_audit_log` — «только добавление»: триггеры БД отвергают `UPDATE`, `DELETE`, `TRUNCATE`; в API нет ручек изменения.
Запись и сама операция — в **одной транзакции** (нет записи — нет изменения). Отказанные попытки (заблокировать себя/админа,
удалить общий файл) пишутся с `result = denied`. Пароли, токены, cookie и подобные ключи в `details` не попадают.

## Производительность

На 50 000 пользователей, 120 000 строк активности и 60 000 тренировок (локальный PostgreSQL): обзор ≈150 мс, список
пользователей 5–30 мс, поиск по подстроке 100–120 мс, остальные списки ≤190 мс. Поиск по подстроке (`ILIKE '%…%'`) сканирует
таблицу; при сотнях тысяч пользователей добавьте индекс `pg_trgm`.
