# Мобильное приложение (Android, React Native + Expo)

Код приложения лежит в `mobile/`. Здесь — то, что приложению нужно от backend.

Полный контракт API — [`docs/openapi.json`](openapi.json) (то же без админских маршрутов: [`docs/ios/openapi-mobile.json`](ios/openapi-mobile.json)). Файлы выгружаются из
приложения (`python scripts/export_openapi.py` в `backend/`), руками их не правят; тест не даст слить изменение API без обновлённого контракта.

## Вход по токену

`POST /api/auth/mobile/login` — тело как у `/api/auth/login` (`email`, `password`). Работает только при
`MOBILE_AUTH_ENABLED=true`, иначе `404`.

Проверки те же, что у входа на сайте (общая функция `_verify_login`): лимиты по IP и по адресу, блокировка после
серии неудач, одинаковое время ответа для неизвестных адресов, заблокированный аккаунт, неподтверждённая почта.

Ответ: пользователь (как у `/auth/me`) плюс

| Поле | Значение |
|---|---|
| `access_token` | обычный токен сессии; приложение хранит его только в `expo-secure-store` |
| `expires_at` | момент, до которого сессия действует при простое |

Cookie не ставится, `csrf_token` не отдаётся. Токен шлётся как `Authorization: Bearer <access_token>`; для запросов
с Bearer CSRF не нужен. Выход — `POST /api/auth/logout` (сессия отзывается на сервере), список и завершение
сессий — `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{id}`.

`POST /api/auth/mobile/verify-email` — подтверждение почты с автовходом: тело как у `/verify-email`, в ответе `session` (как у mobile/login) или `null` для заблокированного аккаунта или аккаунта с 2FA.

`MOBILE_AUTH_ENABLED=true` включает приём Bearer для всех маршрутов (так же, как `BEARER_AUTH_ENABLED`).

## Минимальная версия приложения

Чтобы ломающее изменение API не дошло до приложения, которое его не поймёт, сервер умеет потребовать обновление.

**Что должно делать приложение.**
1. В каждом запросе слать заголовки `X-Client-Platform: ios` (или `android`) и `X-Client-Version: 1.4.0` (версия сборки из магазина, только числа через точку).
2. При запуске читать `GET /api/app-config` (публичный, без входа):

```json
{ "api_version": 1,
  "platforms": { "ios": { "min_version": "1.4.0", "latest_version": "1.6.0", "update_url": "https://apps.apple.com/…" },
                 "android": { "min_version": null, "latest_version": null, "update_url": null } },
  "client": { "platform": "ios", "version": "1.3.0", "update_required": true, "update_available": true } }
```

`client` есть, только если приложение передало заголовки. `update_required: true` — показать экран «Обновите приложение» со ссылкой `update_url` и не работать дальше. `update_available: true` — только предложить обновиться, не заставляя.
3. Любой ответ `426` с `error.code = client_update_required` (`error.min_version`, `error.update_url`) означает то же самое: показать этот экран. Так приложение узнаёт и в середине работы, если версию подняли.

**Что делает сервер.** Если `MIN_CLIENT_VERSION_<IOS|ANDROID>` задана и версия приложения меньше (сравнение по числам: `1.10` новее `1.9`, `1.4` = `1.4.0`), любой запрос `/api/…` получает `426`, не доходя до маршрута. Не затрагиваются: сайт (он этих заголовков не шлёт), `GET /api/app-config`, `GET /api/health`, приложение без заголовков или с нечитаемой версией (такое не повод блокировать). Старая версия приложения, которая заголовков не шлёт, этим способом не останавливается — поэтому заголовки нужно добавить в приложения **до** первого повышения минимума.

**Как поднять минимум.** Выложить в магазин версию, понимающую новый API; задать `MIN_CLIENT_VERSION_…` (и `LATEST_…`, ссылки) в `.env` сервера, пересоздать backend. Пока в `.env` пусто, ничего не меняется.
