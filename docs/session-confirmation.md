# Подтверждение проведённого занятия (TR-01, TR-02)

Задачи TR-01…TR-22 на доске, метка «Подтверждение занятия». Они заменяют карточку #40 («нормальное подтверждение проведения занятия»)
и части REF-09 (#16: неявка, автоподтверждение 48 ч, споры).

## 1. Что есть сейчас (TR-01, проверено по коду 11.11.2026)

### Как занятие становится «проведённым»

| Путь | Кто | Условия | Что меняет |
|---|---|---|---|
| `POST /api/bookings/{id}/complete` — «Тренировка проведена» (`api/routes/bookings.py`) | тренер записи | запись `confirmed`, занятие началось, не отменено | тренировка `completed`; **`earnings.confirm_session`** (`session_confirmed_at`); игроку просьба об отзыве. Повтор безопасен |
| `PUT /api/trainings/{id}` с `status: completed` (`api/routes/trainings.py`) | владелец тренировки — у занятия по записи это **игрок** (`created_by`) | никаких: хоть до начала | только тренировка `completed`; начисление **не** подтверждается |
| Поздняя отмена игроком (`services/cancellations.py`, REF-07) | игрок | меньше `CANCEL_FREE_HOURS` до начала | `confirm_session`: оплата остаётся тренеру |
| Оплата пришла, когда тренировка уже `completed` (`services/payments.py`) | — | — | начисление создаётся сразу подтверждённым |

Второй путь — не только API: сайт и Android сами ставят `completed` после выполнения плана тренировки (`TrainingDetail.tsx`,
`mobile/src/app/workout/[id].tsx`), на iPhone есть пункт меню «Отметить проведённой» (`TrainingDetailView.swift`).

### Как деньги тренера доходят до вывода

`trainer_earnings`: `pending` → (`session_confirmed_at` заполнено) → `available`. Выпуск — только при подтверждённом занятии:
- `EARNING_RELEASE_MODE=admin` (так на проде): финансовый администратор выпускает каждое начисление вручную;
- `auto_after_hold`: само через `EARNING_HOLD_HOURS` (72) после подтверждения (`release_due_earnings` в финансовом такте фонового цикла).

Администратор может заморозить начисление (`held`) и снять заморозку — это готовая основа для спора (TR-13). Возврат уменьшает начисление
(`reversed_kopecks`), а если деньги уже выведены — записывает долг тренера (`trainer_debt`).

### Что открывает отзывы

`bookings.is_completed`: тренировка `completed` **или** прошло время окончания. Подтверждения для этого не нужно.

### Чего нет

- подтверждения игроком, одноразового кода, сообщения о проблеме и спора;
- автоподтверждения: если тренер не нажал «проведена», начисление остаётся `pending` навсегда — и **администратор тоже не может его выпустить**
  (`release_earning` требует `session_confirmed_at`);
- напоминаний о подтверждении.

### Найденные ошибки (есть на проде)

1. **Игрок может отметить оплаченное занятие проведённым** — штатной кнопкой, в том числе до начала. Проверено тестом на настоящей базе:
   отметка за 48 ч до начала → `200`; запись больше нельзя отменить (`can_cancel: false`); потом тренер нажимает «Тренировка проведена» → `200`,
   но начисление остаётся неподтверждённым (маршрут видит `completed` и выходит раньше), то есть деньги тренера застревают.
2. **Игрок может перенести занятие по записи** (`training_date`, `start_time`, `duration_minutes`) без тренера; время в записи (`bookings.starts_at`)
   остаётся старым. Проверено тем же тестом.
3. По коду (не запускал): тренировку отменённой записи можно вернуть в `scheduled` — проверка запрещает только переход в `cancelled`.

### Что переиспользуем

- `session_confirmed_at` и `confirm_session` — единственные ворота «занятие подтверждено» для денег: TR-12 ставит их по итогу окна, а не по кнопке тренера.
- `held` / `unhold` — блокировка спорных начислений (TR-13); долг тренера — для уже выведенных денег.
- Таблица истории «одна строка на запись», как `booking_cancellations` (REF-05) — для подтверждений (TR-03).
- Уведомления с `send_at` и `dedup_key` — напоминания на 24 и 47 ч (TR-10, TR-11) без дублей.
- Фоновый финансовый такт (`reconcile.run_finance_tick`) — место для автоподтверждения (TR-09).
- Ограничение попыток (`rate_limits`) и хеширование секретов — для кода (TR-04, TR-08).

**Зависимость:** время занятия сейчас хранится как время на стене в UTC и сравнивается с настоящим временем (для Москвы сдвиг 3 ч). Таймеры
24/47/48 ч надо считать от исправленного времени — этим занимается отдельная задача.

## 2. Статусы и переходы (TR-02, черновик — ждёт решений из раздела 3)

Окно подтверждения открывается, когда занятие закончилось (`starts_at + duration`). Состояние записи — одно поле, переходы только вперёд:

```
awaiting ──(игрок подтвердил | тренер ввёл верный код)──────────────► confirmed
awaiting ──(48 ч без спора)─────────────────────────────────────────► auto_confirmed
awaiting ──(любая сторона сообщила о проблеме)───────────────────────► disputed ──(администратор)──► confirmed | refunded
```

- Отметка тренера («проведена», TR-06) записывается, но окно не закрывает и деньги не открывает.
- `confirmed` и `auto_confirmed` ставят `session_confirmed_at` → дальше обычный путь выпуска (удержание, админ или авто).
- `disputed` замораживает начисление (`held`); автоподтверждение спорную запись не трогает. Разрешает администратор: выпуск денег или возврат
  существующей машиной возвратов.
- Сообщить о проблеме можно только пока окно открыто. После `confirmed` / `auto_confirmed` — только через поддержку.
- Повторные запросы безопасны: второе подтверждение возвращает то же состояние; фоновая задача не меняет уже закрытое окно.

## 3. Решения, которые нужны от людей

1. Закрывает ли окно **одно** подтверждение игрока (или верный код), или нужны обе стороны?
2. Удержание после подтверждения: оставить `EARNING_HOLD_HOURS` (72 ч) поверх окна 48 ч (итого до 5 дней) или не держать, если подтвердил игрок / код?
3. Код — только для очных занятий (как в TR-07), онлайн подтверждается игроком или через 48 ч?
4. Неявка игрока по заявлению тренера: оплата остаётся тренеру после проверки администратором — или как поздняя отмена, без проверки?
