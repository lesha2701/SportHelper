# Фото: оптимизация перед загрузкой на Яндекс Диск

Все фото, которые загружают пользователи, **проверяются по содержимому, поворачиваются по EXIF, уменьшаются
до нужного размера и сохраняются в WebP** (логотипы — в PNG/WebP без потерь). Оригинал на Диск не попадает.
Код: `backend/app/services/images.py` (обработка) и `backend/app/services/uploads.py` (`store_image_or_raise`).

## Профили

| Профиль | Где используется | Предел | Формат / качество | Миниатюра |
|---|---|---|---|---|
| `avatar` | аватар пользователя | 512 × 512 | WebP, 85 | — |
| `team_logo` | логотип команды | 1024 × 1024 | без потерь: WebP lossless или PNG — что меньше (для JPEG-источника WebP 90) | — |
| `listing_photo` | фото объявления тренера | 1600 × 1200 | WebP, 82 | 480 px |
| `gallery_photo` | галерея достижений | 1920 по длинной стороне | WebP, 85 | 480 px |
| `exercise_photo` | фото упражнения | 1600 по длинной стороне | WebP, 82 | 480 px |
| `report_photo` | фото отчёта о тренировке и ответа на задание | 1600 по длинной стороне | WebP, 82 | — |

* Предел учитывает ориентацию: рамка 1600 × 1200 для вертикального фото превращается в 1200 × 1600.
* Фото никогда не увеличивается и не обрезается, пропорции сохраняются.
* Прозрачность сохраняется (RGBA); полностью непрозрачный альфа-канал отбрасывается.
* EXIF (в том числе геолокация), XMP и IPTC удаляются; ICC-профиль цвета сохраняется.
* **Уже лёгкий файл не пережимается:** если без изменения размера и без метаданных WebP получается
  не меньше чем на 15 %, остаётся исходный файл (с исходным форматом).
* Миниатюры (`files.thumb_disk_path`) делаются только для фото, которые показываются в списках;
  картинка, которая и так не больше ~620 px, миниатюру не получает.

## Защита

* Размер ≤ `MAX_IMAGE_SIZE_MB`; формат определяется по содержимому (JPEG, PNG, WebP, GIF), а не по имени и `Content-Type`.
* Число пикселей проверяется по заголовку, до декодирования (`IMAGE_MAX_PIXELS`); JPEG декодируется сразу в уменьшенном
  масштабе (`draft`), поэтому 48-мегапиксельное фото не занимает память целиком.
* Повреждённые, обрезанные и анимированные файлы отклоняются с понятным русским сообщением.
* Одновременно обрабатывается не больше `IMAGE_OPTIMIZE_CONCURRENCY` фото; работа идёт в отдельном потоке, не блокируя API.
* Имя файла очищается (без путей, управляющих символов, ≤ 80 символов) и получает расширение сохранённого формата;
  путь на Диске строится только из идентификаторов и никогда не зависит от имени. `Content-Disposition` безопасен
  для любых имён, в том числе старых.
* Если запись в базу не удалась после загрузки, загруженные байты удаляются с Диска.

## Раздача

`GET /api/files/{id}` отдаёт файл с `Cache-Control` (публичные — `public, max-age=86400`, остальные — `private,
max-age=3600`: идентификатор файла не меняется, замена фото даёт новый). `GET /api/files/{id}?size=thumb` отдаёт
миниатюру, а если её нет (старые файлы, маленькие и непревьюируемые картинки) — сам файл. Права проверяются так же,
как для основного файла.

## Старые файлы

Не изменяются и не удаляются: их URL, пути и MIME прежние, колонка `thumb_disk_path` у них `NULL`.
Фоновая очистка удалённых файлов (`purge_soft_deleted_files`) теперь удаляет и миниатюру.

## Логи

Одна строка на загрузку, без имён, путей и токенов:

```
Image optimized: type=gallery_photo original=3.0MB optimized=375KB saved=87.7% duration=326ms size=1440x1920 thumbnail=60KB
```

## Возможный следующий шаг (не реализовано)

Безопасное пережатие уже загруженных файлов — отдельный скрипт, который сначала работает в режиме `--dry-run`
(показывает ожидаемую экономию), для каждого файла загружает новую версию под новым именем, обновляет
`files.disk_path/mime_type/size_bytes` в одной транзакции и только после успеха ставит старый файл в очередь
на мягкое удаление (хранится `SOFT_DELETE_RETENTION_DAYS`).
