# Отмена записи и возврат: контракт API (REF-04) и схема данных (REF-05)

Решения приняты 10.11.2026 (см. `docs/refunds.md`, раздел 6). Этот документ описывает **что будут делать маршруты**, чтобы сайт, iPhone и
Android строились параллельно. Маршруты реализованы (REF-06, REF-07) и есть в `docs/openapi.json`; тесты — `tests/test_booking_cancellation.py`.
Схема данных (миграция `0043`) уже готова и проверена на PostgreSQL.

## 1. Правила (принятые решения)

| Кто отменяет | Когда | Что возвращается игроку | Комиссия платформы | Тренеру |
|---|---|---|---|---|
| Игрок | за `CANCEL_FREE_HOURS` (24 ч) и раньше до начала | 100% | возвращается целиком | начисление снимается |
| Игрок | позже, чем за 24 ч, но до начала | 0% | остаётся у платформы | сохраняет оплату (удержание 72 ч, как после проведённого занятия) |
| Тренер | в любой момент до начала, причина обязательна | 100% | возвращается целиком | начисление снимается |
| любой | запись не оплачена | ничего | — | — |
| любой | занятие уже началось, завершено или отменено | нельзя (`409`) | — | — |

- Отменить можно только **подтверждённую** запись (`confirmed`). Ожидающую (`pending`) тренер по-прежнему отклоняет (`/decline`), игрок отдельно её не отменяет.
- Перенос, неявка и спор в этот релиз **не входят**: «перенос» = отмена и новая запись; неявку и спор решает администратор вручную через существующий возврат.
- Претензия после занятия: игрок подаёт жалобу (`complaints`) в течение 7 дней, администратор возвращает деньги вручную, как сейчас.
- Деньги идут через существующую машину возвратов (`services/refunds.py`): резерв суммы в платеже, запрос в ЮKassa с ключом идемпотентности, проводки только после
  подтверждения ЮKassa, долг тренера, если деньги уже выведены. Правило «возврат делает только администратор» меняется на «отмена по правилу запускает возврат сама».

Настройка: `CANCEL_FREE_HOURS` (целое, по умолчанию `24`, от `0` до `720`).

## 2. Маршруты

### `GET /api/bookings/{booking_id}/cancel-preview`
Что произойдёт, если отменить **сейчас**. Ничего не меняет. Нужен, чтобы экран показал «Вернём 100%» или «Деньги не вернутся» **до** нажатия кнопки.

Доступ: игрок или тренер этой записи; чужая запись выглядит как несуществующая (`404`).

Ответ `200`:
```json
{
  "booking_id": "…",
  "cancelled_by_role": "athlete",
  "policy": "athlete_early",
  "hours_before_start": 52.5,
  "free_cancel_until": "2026-11-20T09:00:00Z",
  "paid_kopecks": 500000,
  "refund_percent": 100,
  "refund_kopecks": 500000,
  "trainer_keeps_payment": false
}
```
- `policy`: `unpaid` | `athlete_early` | `athlete_late` | `coach`.
- `free_cancel_until`: до какого момента игрок отменяет бесплатно; `null`, если оплаты нет или отменяет тренер.
- `trainer_keeps_payment`: `true` только для `athlete_late`.
- Ошибки: те же `409`, что и у `POST /cancel` (см. раздел 3), кроме `reason_required`.

### `POST /api/bookings/{booking_id}/cancel`
Отменяет подтверждённую запись.

Тело:
```json
{ "reason": "Заболел" }
```
- `reason`: строка до 500 знаков. Для игрока необязательна. Для тренера **обязательна** (от 3 знаков), иначе `422 reason_required`.

Что происходит (одна транзакция, запись и платёж блокируются):
1. Проверка доступа и состояния. Повторная отмена уже отменённой записи возвращает `200` с тем же состоянием, второго возврата не будет.
2. Расчёт по правилу (`policy`, `refund_percent`, `refund_kopecks`) и запись в `booking_cancellations` (снимок: кто, когда, за сколько часов, сколько оплачено).
3. Запись → `cancelled`, связанная тренировка → `cancelled` (в календарях пропадает как отменённая), окно в расписании тренера освобождается, напоминания по ней снимаются.
4. Если есть сумма возврата, создаётся возврат (`refunds`, тип `payment`, `requested_by` = отменивший) и отправляется в ЮKassa.
5. Начисление тренера: при возврате снимается (`reversed`); при `athlete_late` помечается «занятие подтверждено» и уходит на обычное удержание 72 часа.
6. Уведомление (категория `booking_decided`) второй стороне (отменившему оно не нужно: он видит результат в ответе); по завершении возврата приходит существующее «Возврат выполнен».

Отмена **не зависит от ЮKassa**: если провайдер не отвечает, запись всё равно отменяется, возврат остаётся `requested` и отправляется фоновой сверкой
(та же идемпотентность). В ответе тогда `refund_status: "pending"`. Деньги игрока при этом нигде не теряются: резерв стоит в платеже.

Ответ `200`: `BookingOut` (раздел 4) уже со статусом `cancelled` и заполненным `cancellation`.

### `GET /api/bookings/{booking_id}/money` (REF-13)
История денег одной записи: платёж и все возвраты по ней. Доступ: игрок или тренер записи, чужая запись — `404`. Ничего не меняет.

```json
{
  "booking_id": "…", "viewer_role": "athlete", "currency": "RUB",
  "payment": { "status": "paid", "gross_kopecks": 250000, "paid_at": "2026-11-18T09:00:00Z",
               "trainer_kopecks": null, "platform_fee_kopecks": null },
  "refunds": [ { "id": "…", "amount_kopecks": 250000, "status": "succeeded", "source": "cancellation", "reason": "Заболел",
                 "created_at": "…", "completed_at": "…", "trainer_refund_kopecks": null } ],
  "refunded_kopecks": 250000, "cancelled_at": "…", "cancellation_policy": "athlete_early"
}
```
- `payment`: `null`, пока записи не оплачивали. `trainer_kopecks`, `platform_fee_kopecks` и `trainer_refund_kopecks` заполнены **только для тренера** (его доля и комиссия платформы); игроку они не нужны.
- `refunds[].status`: `pending` (создан, ждёт банк) | `succeeded` | `failed` (банк отказал, решает администратор).
- `refunds[].source`: `cancellation` (по отмене записи) | `automatic` (оплата пришла после отмены и вернулась сама) | `administrator` (вручную).
- `refunds[].reason`: причина отмены, если возврат её; **внутренняя заметка администратора наружу не отдаётся** (`null`).
- Возвраты за повторную оплату (`duplicate`) сюда не входят: это инцидент для администратора.
- История тренера по всем операциям с балансом уже есть: `GET /api/finance/operations`.

### Что меняется в существующих маршрутах (только добавления)
- `GET /api/bookings/me` и `GET /api/bookings/coach` теперь включают отменённые записи (`status = "cancelled"`) и новые поля в `BookingOut`.
- `PATCH /{id}/plan`, `/complete`, `/pay`, `/reviews`: для отменённой записи отвечают `409` (`booking_not_confirmed`, `booking_closed`), как для закрытой.
- Оплата, пришедшая **после** отмены (игрок открыл страницу ЮKassa до отмены и оплатил позже): сервер возвращает её **целиком** автоматически, причина «запись отменена»;
  как и сейчас, фиксируется инцидент `paid_booking_closed` для администратора.

## 3. Ошибки

Формат как везде: `{"error": {"code", "message"}}`.

| HTTP | `code` | Когда |
|---|---|---|
| 404 | — | запись не найдена или чужая |
| 409 | `booking_not_confirmed` | запись ожидает ответа, отклонена, истекла (отменять нечего) |
| 409 | `session_started` | занятие уже началось или время вышло |
| 409 | `session_completed` | занятие отмечено проведённым |
| 409 | `session_cancelled` | связанная тренировка уже отменена другим способом |
| 422 | `reason_required` | тренер не указал причину |
| 422 | `validation_error` | `reason` длиннее 500 знаков |
| 502 | `payment_provider_error` | **не используется в `/cancel`**: недоступность ЮKassa отмену не блокирует |
| 503 | `payments_unavailable` | не используется в `/cancel` по той же причине |

## 4. Поля `BookingOut` (добавляются)

```json
{
  "status": "cancelled",
  "can_cancel": false,
  "cancellation": {
    "cancelled_by_role": "athlete",
    "cancelled_at": "2026-11-20T10:15:00Z",
    "reason": "Заболел",
    "policy": "athlete_early",
    "refund_percent": 100,
    "refund_amount_kopecks": 500000,
    "refund_status": "pending"
  }
}
```
- `can_cancel`: можно ли отменить прямо сейчас (запись `confirmed`, занятие не началось, не завершено и не отменено). Кнопку «Отменить» показывают по нему.
- `cancellation`: `null`, пока запись не отменена.
- `refund_status`: `none` (нечего возвращать или 0%) | `pending` (создан, ждёт ЮKassa) | `succeeded` | `failed` (провайдер отклонил, администратор решает вручную).
- `cancelled_at` — настоящий момент отмены: клиенты показывают его в часовом поясе читателя. Время занятия (`starts_at`, `free_cancel_until`) —
  «настенное» время платформы (`SESSION_TIMEZONE`, Москва) с меткой UTC: `10:00Z` = 10:00 по Москве. Его показывают как есть (часы UTC)
  и не сравнивают с часами устройства; началось ли занятие, говорит сервер (`has_started`, `can_cancel`). Окно бесплатной отмены
  и «занятие началось» сервер считает по тем же часам (REF-19).
- Если при отмене платить было не за что (`policy: unpaid`), а оплата всё-таки пришла позже (страница оплаты была открыта заранее),
  сервер возвращает её сам. Тогда `refund_status` и `refund_amount_kopecks` рассказывают об этом возврате, а `policy` остаётся `unpaid`
  (так было решено в момент отмены). Клиенты показывают строку о деньгах по `refund_status` при любой `policy`, кроме `athlete_late`.
- При `failed` финансовые администраторы получают инцидент `refund_failed`: и когда ЮKassa отказала сразу, и когда отменила возврат позже.
- `payment_status` (уже есть): при возврате становится `refund_pending`, затем `refunded` (`not_required` и `unpaid` не меняются).
- `status` теперь может быть `cancelled`; клиенты, которые не знают этого значения, должны показывать «Отменена» и не ломаться.

## 5. Схема данных (миграция 0043)

Одна таблица `booking_cancellations` (история отмен), по записи не более одной строки:

| Поле | Смысл |
|---|---|
| `booking_id` (уникальное) | отменённая запись |
| `cancelled_by`, `cancelled_by_role` | кто (`athlete` / `coach`) |
| `reason` | причина |
| `session_starts_at`, `hours_before_start` | снимок: когда было занятие и за сколько часов отменили |
| `policy` | `unpaid` / `athlete_early` / `athlete_late` / `coach` |
| `paid_kopecks`, `refund_percent`, `refund_kopecks` | сколько было оплачено и сколько возвращается |
| `refund_id` | возврат, который несёт деньги (один возврат принадлежит одной отмене) |

Что база запрещает сама, независимо от приложения: вторую отмену той же записи, возврат больше оплаты, «0% с суммой» и «сумма при 0%», возврат при `unpaid`
и при `athlete_late`, неизвестную роль или правило, `refund_id` без суммы. Статус `bookings.status = 'cancelled'` уже допускался миграцией `0020`, платежи и проводки не менялись.

Проверено 11 тестами на настоящей PostgreSQL (`tests/test_booking_cancellations_schema.py`).

## 6. Что должен сделать каждый клиент

| Клиент | Задача |
|---|---|
| Сайт (REF-14, 15) | кнопка «Отменить» по `can_cancel`; окно с итогом из `cancel-preview` («Вернём 100%» / «Деньги не вернутся»); у тренера поле причины; в карточке отменённой записи — кто и когда отменил, причина, статус возврата |
| iPhone (REF-16) | то же, в `BookingsService` методы `cancelPreview` и `cancel`; статус «Отменена»; UI-тесты на оба сценария |
| Android (REF-17) | то же по `docs/openapi.json`; проверить, что `cancelled` не ломает списки |

## 7. Сценарии для тестов (REF-18, REF-19)

1. Игрок отменяет оплаченную запись за 48 ч → возврат 100%, комиссия вернулась, начисление тренера снято, окно свободно, тренировка отменена.
2. Игрок отменяет за 2 ч → возврата нет, тренер сохраняет оплату, начисление подтверждено и ждёт 72 ч.
3. Тренер отменяет без причины → `422`; с причиной → возврат 100%.
4. Отмена неоплаченной подтверждённой записи → просто отмена, возврата нет.
5. Повторная отмена → `200`, второго возврата нет (идемпотентность).
6. Отмена во время начавшегося занятия → `409 session_started`; после «проведена» → `409 session_completed`.
7. ЮKassa недоступна → отмена проходит, возврат `pending`, после восстановления доходит сверкой.
8. Деньги тренера уже выведены → доля тренера превращается в долг, инцидент `trainer_debt` (это правило существующей машины возвратов, проверено в `test_finance.py`; при отмене до начала начисление ещё не доступно к выводу, а при поздней отмене игрока возврата нет).
9. Оплата, пришедшая после отмены → возвращается целиком, инцидент остаётся.
10. Чужая запись → `404`; игрок отменяет как тренер (чужая роль) → `404`.
11. Отмена и «Тренировка проведена» не пересекаются по времени: отмена возможна только до начала, отметка «проведена» — только после (`session_not_started`); отмена после отметки → `409 session_completed`.

**Проверено на локальном стеке (REF-19, 11.11.2026).** Через настоящий API, с заглушкой ЮKassa, умеющей возвраты, недоступность и отказ,
прошли сценарии 1–7, 9, 10, а также: подтверждение возврата вебхуком `refund.succeeded` и сверкой без вебхука; отказ ЮKassa сразу (`400`)
и отмена возврата позже; две одновременные отмены (один возврат); история денег у обеих сторон (доля тренера видна только тренеру);
проводки сходятся, ни один возврат не больше оплаты, начисления неудачных возвратов сами тренеру не уходят. Найдено и исправлено:
не было инцидента при немедленном отказе ЮKassa; карточка молчала про оплату, пришедшую после отмены; время отмены показывалось по UTC.
Чек-лист выпуска — [`release-refunds.md`](release-refunds.md).
