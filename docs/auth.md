# Регистрация, вход и безопасность аккаунта

SportArena Global — обычный сайт с собственными аккаунтами: email + пароль,
подтверждение почты, серверные сессии. Telegram **не нужен** ни для входа, ни
для работы сайта; он остался необязательным каналом уведомлений и способом
перенести старый аккаунт (см. [«Перенос старых аккаунтов»](#перенос-старых-telegram-аккаунтов)).

## Как это устроено

| Вопрос | Решение |
|---|---|
| Идентификатор пользователя | `users.id` (UUID). Он же использовался и раньше, на него ссылаются все таблицы, поэтому тренировки, брони, команды и уведомления не затронуты. `telegram_id` стал необязательным атрибутом. |
| Пароль | Только хэш **Argon2id** (`argon2-cffi`, параметры RFC 9106 «low memory», настраиваются). Минимум 12 символов, максимум 512, любой Unicode, **никаких** требований к заглавным/цифрам/символам. Пароль нормализуется (NFKC), чтобы одна и та же фраза с разных клавиатур давала один хэш. |
| Слабые пароли | Встроенный список частых паролей и тривиальных шаблонов; пароль не может содержать email или совпадать с именем. Дополнительно (флаг `PASSWORD_BREACH_CHECK`) — проверка по базе утечек Have I Been Pwned методом k-anonymity: наружу уходят только 5 символов SHA-1 хэша, пароль никуда не передаётся; при недоступности сервиса проверка пропускается. |
| Email | Нормализуется (обрезка, проверка формата, нижний регистр), уникален **на уровне БД**: `UNIQUE INDEX users_email_unique ON users (lower(email))` + `CHECK (email = lower(email))`. Подтверждается ссылкой из письма; до этого войти нельзя. |
| Сессия | Случайный 256-битный идентификатор в **HttpOnly**-cookie. В БД лежит только его SHA-256, поэтому утечка таблицы не даёт рабочих сессий. Сессии можно просмотреть и завершить по одной или все сразу. |
| Cookie | `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`; в production — `Secure` и префикс `__Host-`. Срок: 30 дней без активности (скользящий), но не дольше 90 дней с момента входа. |
| Хранение в браузере | Ничего секретного в `localStorage`/`sessionStorage`. Единственное, что держит страница, — CSRF-токен в памяти. |
| CSRF | Токен привязан к сессии: `HMAC(JWT_SECRET, session_token)`. Отдаётся в ответе `/api/auth/login` и `/api/auth/me`, возвращается в заголовке `X-CSRF-Token` на каждый `POST/PUT/PATCH/DELETE`. Плюс проверка заголовка `Origin` у любых изменяющих запросов. Запросы с `Authorization: Bearer <session>` (скрипты, тесты) CSRF не требуют — у них нет автоматически прикрепляемых cookie. |
| Защита от перебора | (1) счётчик неудач в БД: 5 ошибок → блокировка входа на 15 минут; (2) ограничения по IP и по целевому email (скользящее окно) на `login`, `register`, `forgot-password`, `resend-verification`, `reset-password` и др.; (3) одинаковое время ответа для существующих и несуществующих адресов (холостая проверка Argon2). Ответ `429` содержит `Retry-After`. |
| Одноразовые ссылки | Подтверждение email (24 ч), восстановление пароля (**30 мин**), смена email (24 ч), перенос Telegram-аккаунта и привязка Telegram (30 мин). Случайные 256 бит, в БД — только хэш, погашаются атомарно (`UPDATE … RETURNING`), новая ссылка того же типа отменяет прежнюю. |
| Нейтральные ответы | «Забыли пароль» и «Отправить письмо ещё раз» отвечают одинаково для любого адреса. Регистрация сообщает, что адрес занят (иначе человек не поймёт, что у него уже есть аккаунт), но ограничена по IP. |
| Логи | Пароли, токены и тела писем не пишутся в production-логи. Без SMTP в `APP_MODE=main` в лог уходит только факт, что письмо не отправлено. |
| Роли | Один аккаунт — несколько ролей: профили игрока и тренера (как и раньше) + переключатель `active_mode`. При регистрации можно выбрать роль, это лишь подсказка для первого экрана. Администратор определяется **только** конфигурацией сервера (`ADMIN_EMAILS`), через API его получить нельзя. |

## Схема БД и миграция 0031

Файл [`database/patches/0031_web_auth.sql`](../database/patches/0031_web_auth.sql) применяется автоматически
при старте backend, как и все предыдущие патчи.

- `users`: `telegram_id` теперь `NULL`-able; новые колонки `email`, `email_verified_at`, `password_hash`,
  `password_changed_at`, `failed_login_count`, `locked_until`, `terms_accepted_at`, `terms_version`,
  `preferred_role`, `deletion_requested_at`, `deleted_at`.
- Новые таблицы: `user_sessions`, `auth_tokens`, `user_mfa`.
- Удалена `browser_login_tokens` — временные (5 минут) токены прежнего входа через бота, пользовательских данных в ней нет.
- Все операторы идемпотентны (`IF NOT EXISTS`, проверки в `DO $$`): повторный прогон безопасен — это проверяется тестом.

**Что происходит с существующими пользователями:** ничего не удаляется и не копируется. Строка пользователя
остаётся (тот же `id`, тот же `telegram_id`), у неё просто нет email и пароля. Общего или предсказуемого
временного пароля нет ни у кого. Аккаунты не склеиваются автоматически ни по имени, ни по неподтверждённому email.

## API

Все ошибки — в формате `{"error": {"code", "message", "field"?, "retry_after"?}}`.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /api/auth/register` | Регистрация, письмо с подтверждением | публично |
| `POST /api/auth/verify-email` | Подтверждение email по токену | публично |
| `POST /api/auth/resend-verification` | Повторная отправка письма (нейтральный ответ) | публично |
| `POST /api/auth/login` | Вход, ставит cookie, возвращает пользователя и `csrf_token` | публично |
| `GET /api/auth/me` | Текущий пользователь + `csrf_token` | сессия |
| `POST /api/auth/logout` | Завершить текущую сессию | любой |
| `POST /api/auth/logout-all` | Завершить все сессии | сессия |
| `GET /api/auth/sessions` | Список активных сессий (устройство, IP, активность) | сессия |
| `DELETE /api/auth/sessions/{id}` | Завершить конкретную сессию (только свою) | сессия |
| `POST /api/auth/forgot-password` | Письмо со ссылкой (нейтральный ответ) | публично |
| `POST /api/auth/reset-password` | Новый пароль по токену; все сессии завершаются; письмо-уведомление | публично |
| `POST /api/auth/change-password` | Смена пароля (нужен текущий); остальные сессии завершаются | сессия |
| `POST /api/auth/change-email` | Запрос смены email (нужен пароль); письмо на новый адрес, предупреждение на старый | сессия |
| `POST /api/auth/confirm-email-change` | Подтверждение нового email | публично |
| `POST /api/auth/account/delete` / `…/cancel` | Запрос удаления аккаунта (нужен пароль) / отмена | сессия |
| `POST /api/auth/telegram/link` / `unlink` | Подключить/отвязать Telegram для уведомлений | сессия |
| `POST /api/auth/claim/inspect`, `POST /api/auth/claim` | Перенос старого Telegram-аккаунта (по ссылке от бота) | публично, по токену |
| `GET /api/auth/mfa`, `POST …/mfa/setup`, `…/enable`, `…/verify`, `…/disable` | TOTP для администраторов | сессия |

Удалены: `POST /api/auth/telegram`, `POST /api/auth/browser/start|poll`, `POST /api/auth/dev-login*`.

**Публичные** (без входа, только чтение): `GET /api/coach-listings` (+ `/{id}`, `/{id}/slots`),
`GET /api/coaches/{id}/profile|listings|reviews`, `GET /api/profile/media/{coach_id}` (галерея тренера),
`GET /api/files/{id}` — только файлы с уровнем доступа `PUBLIC` (аватары, фото/видео объявлений).
Всё остальное требует сессии. Это гарантирует тест `tests/test_auth_route_coverage.py`: он обходит **все**
маршруты приложения и падает, если какой-то из них отвечает анонимному запросу не `401`, а его нет в явном списке публичных.

## Пользовательские сценарии

- **Регистрация** → письмо → ссылка `/verify-email?token=…` → «Email подтверждён» → вход. На экране «Проверьте почту»
  есть повторная отправка (с паузой 60 с), «Изменить адрес» (форма остаётся заполненной) и «Я подтвердил — войти».
- **Вход** → переход туда, куда человек шёл (`?next=`; принимаются только пути внутри сайта, внешние адреса игнорируются).
- **Запись без аккаунта**: гость открывает каталог, профиль, свободные слоты — всё без регистрации. Нажав «Записаться»,
  попадает на вход/регистрацию с пояснением и после входа сразу видит форму записи **именно этого объявления**
  (`/?book=<id>`).
- **Ссылки-приглашения в команду и deep link из уведомлений** (`/?invite=…`, `/?open=…&id=…`) для гостя ведут через вход и
  возвращают к тому же адресу.
- **Восстановление пароля**: «Забыли пароль?» → нейтральное «Если аккаунт с таким адресом существует, мы отправили письмо» →
  ссылка (30 мин, один раз) → новый пароль → «Пароль изменён» → вход. Все сессии завершены, на почту ушло уведомление.
- **Аккаунт и безопасность** (Профиль → Настройки): email (смена с подтверждением нового адреса и предупреждением на старый),
  пароль, активные сессии (завершить одну / выйти везде), подключение Telegram, 2FA для администраторов, запрос удаления.
- **Выход** возвращает на публичную главную. Если сессия закончилась (истекла или завершена с другого устройства), приложение
  само возвращается к гостевому режиму и объясняет это на странице входа.

### Удаление аккаунта

Запрос подтверждается паролем, на почту уходит уведомление, **14 дней** (`ACCOUNT_DELETION_GRACE_DAYS`) его можно отменить.
Затем фоновая задача **обезличивает** пользователя: email, пароль, Telegram, имя и фото стираются, анкеты игрока/тренера
очищаются, объявления снимаются с публикации, сессии закрываются. Строка пользователя остаётся: тренировки, брони, отзывы и
(в будущем) финансовая история ни при каких условиях не удаляются каскадом — это проверено тестом на реальной БД.
Галерея достижений скрывается; сами загруженные файлы остаются на Яндекс.Диске (удалить их можно существующим
механизмом мягкого удаления файлов), аватар перестаёт показываться.

## Перенос старых Telegram-аккаунтов

Старый аккаунт не может «войти без пароля» через Telegram — этого пути больше нет. Вместо этого Telegram служит
**доказательством владения**:

1. Владелец пишет боту `/start`. Бот видит, что у его Telegram есть аккаунт без подтверждённого email, и присылает кнопку
   «Перенести аккаунт на email» — одноразовую ссылку на `/claim?token=…` (30 минут).
2. На сайте он указывает email и пароль (и принимает документы). **Тот же аккаунт** (тот же `id`, команды, тренировки, брони)
   получает пароль, а адрес уходит на подтверждение.
3. Email записывается в аккаунт только после перехода по ссылке из письма — поэтому чужой адрес занять нельзя.
4. Дальше — обычный вход по email и паролю.

Никакого автоматического слияния: если человек вместо этого зарегистрируется заново, это будет **другой** аккаунт.
Привязать Telegram обратно (для уведомлений) можно в настройках: «Подключить Telegram» → бот → подтверждение.
Один Telegram нельзя привязать к двум аккаунтам.

**План выката для работающего проекта**

1. Сделайте резервную копию БД (`docs/deployment.md`, раздел «Бэкапы»).
2. Заполните в `.env` новые переменные (SMTP, `APP_BASE_URL`, `JWT_SECRET`, `ADMIN_EMAILS`) — см. ниже. Без SMTP письма не уходят и никто не сможет подтвердить email.
3. Обновите код и перезапустите: `docker compose up -d --build`. Миграция применится сама.
4. Напишите пользователям (рассылкой бота `/broadcast`): «Сайт теперь работает без Telegram. Откройте бота, нажмите /start и
   перенесите аккаунт на email». Рекомендуется временно поставить `NUDGE_ENABLED=false`, чтобы напоминания не мешали рассылке.
5. Первого администратора создайте скриптом (ниже) и добавьте его адрес в `ADMIN_EMAILS`.

## Что публично, а что нет

Публично: каталог тренеров, их профили, объявления, свободные даты и отзывы, публичные фото/видео (аватары и медиа
объявлений), главная, юридические документы. Не публично и закрыто сессией: профиль игрока (виден только тренерам по общей
команде/записи), команды, тренировки, задания, матчи, календарь, статистика, брони, уведомления, файлы с уровнем
`PRIVATE`/`TEAM`/`COACHES_ONLY`, галереи игроков, любые действия. В публичных ответах нет email, Telegram, служебных флагов
(проверяется тестом).

## Администраторы и MFA

Администратор — подтверждённый аккаунт, чей email указан в `ADMIN_EMAILS` (регистр не важен). Изменить это можно только на
сервере. Зависимости `require_admin` и `require_admin_mfa` (`backend/app/api/deps.py`) готовы для будущих административных и
**финансовых** маршрутов: `require_admin_mfa` требует включённой двухфакторной защиты (TOTP, RFC 6238) **и** кода, введённого
в текущей сессии за последние `ADMIN_MFA_SESSION_HOURS` часов. Секрет TOTP хранится зашифрованным (Fernet, ключ выводится из
`JWT_SECRET`), резервные коды — хэшами, повтор одного и того же кода запрещён. Настройка — в «Аккаунт и безопасность».
Платёжного модуля пока нет, поэтому финансовых маршрутов тоже нет — защита проверена тестами на тестовом маршруте.

Административные команды **бота** (`/admin`, `/ban`, …) по-прежнему доступны по `ADMIN_TELEGRAM_IDS` и к веб-доступу не относятся.

Создать (или сбросить пароль) подтверждённого пользователя напрямую в БД — например, первого администратора:

```bash
docker compose exec backend python scripts/create_user.py boss@example.com "Босс"
# пароль спросит скрытым вводом; роль администратора выдаёт только ADMIN_EMAILS
```

## Настройка почты

Подойдёт любой SMTP: Яндекс 360 для бизнеса, Mail.ru для бизнеса, Unisender, Mailgun, SendPulse, свой Postfix. Платный сервис не
обязателен — у большинства есть бесплатный тариф на тысячи писем в месяц, этого хватает на подтверждения и сбросы паролей.

1. Создайте почтовый ящик или SMTP-доступ на домене сайта (например `no-reply@sportarenaglobal.ru`).
2. **Настройте DNS домена для отправителя — иначе письма попадут в «Спам»:** SPF (`TXT @ "v=spf1 include:<провайдер> ~all"`),
   DKIM (ключ даёт провайдер) и DMARC (`TXT _dmarc "v=DMARC1; p=none; rua=mailto:you@…"`). Инструкции есть в панели провайдера.
3. Впишите в `.env` на сервере:

   ```env
   SMTP_HOST=smtp.yandex.ru        # адрес из панели провайдера
   SMTP_PORT=465                   # 465 + ssl или 587 + starttls
   SMTP_SECURITY=ssl               # ssl | starttls | none
   SMTP_USERNAME=no-reply@sportarenaglobal.ru
   SMTP_PASSWORD=пароль_приложения
   SMTP_FROM=SportArena Global <no-reply@sportarenaglobal.ru>
   ```
4. Перезапустите: `docker compose up -d backend bot`.
5. Проверка: зарегистрируйте тестовый аккаунт на реальный адрес — письмо должно прийти за секунды. Ошибки отправки видны в
   `docker compose logs backend | grep teamflow.email` (адрес и тема письма, но не ссылка).

**Разработка:** `docker-compose.dev.yml` поднимает Mailpit — все письма оказываются на <http://localhost:8025>, ничего не уходит
наружу. Без Mailpit и SMTP в `APP_MODE != main` ссылка из письма печатается в лог backend.

| `EMAIL_VERIFY_TTL_HOURS`, `PASSWORD_RESET_TTL_MINUTES`, `EMAIL_CHANGE_TTL_HOURS` | `24`, `30`, `24` | Сроки ссылок. |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` | пусто | Почта. |
| `ADMIN_EMAILS`, `ADMIN_MFA_SESSION_HOURS` | пусто, `12` | Администраторы веб-API. |
| `ACCOUNT_DELETION_GRACE_DAYS`, `TERMS_VERSION` | `14`, `2026-10` | Удаление и версия документов. |
| `AUTH_RATE_LIMIT_ENABLED` | `true` | Только для автотестов. |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` | пусто | **Необязательно.** Перенос аккаунтов, уведомления в Telegram, админ-команды бота. |
| `VITE_SUPPORT_EMAIL` (сборка frontend) | пусто | Контактный адрес на страницах «Соглашение»/«Конфиденциальность». |

Удалены: `DEV_AUTH_ENABLED`, `TELEGRAM_AUTH_MAX_AGE_SECONDS`, `JWT_ALGORITHM`, `JWT_EXPIRES_MINUTES` (старые значения в `.env` игнорируются).

## Чек-лист перед production

- [ ] `APP_MODE=main`, домен открыт по **HTTPS** (Caddy из `docker-compose.yml` выпускает сертификат сам).
- [ ] Новый случайный `JWT_SECRET` (не из примера; backend пишет ошибку в лог при дефолтном значении в `APP_MODE=main`).
- [ ] `APP_BASE_URL=https://<домен>`, `CORS_ORIGINS=https://<домен>` (строго один источник, без `*`).
- [ ] Рабочий SMTP, SPF/DKIM/DMARC на домене, проверена доставка реального письма.
- [ ] `ADMIN_EMAILS` заполнен; администратор включил 2FA.
- [ ] `PASSWORD_BREACH_CHECK=true` (исходящий HTTPS-доступ к `api.pwnedpasswords.com`) — по желанию.
- [ ] Резервная копия БД перед выкатом; `/api/health` возвращает `{"status":"ok","database":true}`.
- [ ] Юридические тексты (`/terms`, `/privacy`) прочитаны и согласованы юристом, указан `VITE_SUPPORT_EMAIL`.
- [ ] Старый бот остановлен, если переиспользуется токен (иначе конфликт `getUpdates`).
- [ ] `.env` не в git; на сервере права `chmod 600 .env`.

## Тесты

```bash
cd backend && python -m pytest -q      # 400+ тестов
cd frontend && npm test                # 120+ тестов (Vitest)
```

- `backend/tests/test_auth_*.py` — регистрация, вход, сессии, CSRF, блокировки и ограничения частоты, подтверждение и
  восстановление, смена email/пароля, перенос аккаунтов, роли/администраторы/MFA, удаление, публичный доступ и обход всего API.
- `backend/tests/test_auth_postgres.py` — **настоящий PostgreSQL**: миграция 0031 на базе с существующими пользователями и данными,
  повторный прогон, уникальность email на уровне БД, атомарность одноразовых токенов при гонке, обезличивание без каскадного
  удаления, полный HTTP-сценарий. В CI используется сервис `postgres`; локально — `TEST_DATABASE_URL=postgresql://…` или
  `pip install pgserver` (встроенный PostgreSQL), без обоих тесты пропускаются.
- Остальные backend-тесты работают на in-memory двойниках (`tests/fake_auth.py` повторяет семантику SQL).
