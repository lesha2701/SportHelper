# Деплой на сервер — пошаговый гайд для новичка

Этот гайд проведёт вас с нуля: от «нет ничего» до работающего бота и Mini App
на настоящем сервере, с автоматическими тестами и автодеплоем через GitHub.
Рассчитан на то, что вы никогда раньше этого не делали — идите по шагам по
порядку, не пропуская.

## Что в итоге получится

```
                     ┌─────────────────────────────────────┐
                     │              Ваш VPS                 │
                     │                                       │
  Пользователь ──────┼──▶ Caddy (порты 80/443, HTTPS сам)    │
  (браузер/Telegram) │       │                                │
                     │       ├──▶ статика фронтенда (React)  │
                     │       └──▶ /api/* ──▶ backend (FastAPI)│
                     │                          │              │
                     │                     ┌────┴────┐         │
                     │                     │ Postgres │         │
                     │                     └────┬────┘         │
                     │                          │              │
                     │              bot (тот же образ,        │
                     │              long polling к Telegram)   │
                     └─────────────────────────────────────┘
                              ▲
                              │ git pull + docker compose build/up
                              │ (автоматически при push в main)
                     ┌────────┴────────┐
                     │  GitHub Actions  │ ── прогоняет тесты
                     └─────────────────┘
```

Всё это уже подготовлено в репозитории:
- `backend/Dockerfile` — образ для backend и бота (два разных `command:` одного образа)
- `frontend/Dockerfile` + `frontend/Caddyfile` — собирает React-приложение и раздаёт его через Caddy (автоматический HTTPS-сертификат, без ручной настройки certbot)
- `docker-compose.yml` — связывает всё вместе: Postgres, backend, bot, frontend/Caddy
- `.env.production.example` — шаблон конфигурации для сервера
- `.github/workflows/ci.yml` — тесты на каждый push + автодеплой на сервер при push в `main`

Дальше — что нужно сделать руками, по шагам.

## Шаг 1. Купить VPS (виртуальный сервер)

Нужен сервер с Ubuntu, минимум **2 ГБ RAM / 2 vCPU / 40 ГБ SSD** — этого с
запасом хватит на Postgres + backend + bot + Caddy для команды/клуба.

**Рекомендация: [Timeweb Cloud](https://timeweb.cloud/)** — российский
провайдер, простая понятная панель на русском, тариф от ~300–400 руб/мес
за нужные характеристики, принимает российские карты. При создании сервера:
- Образ: **Ubuntu 24.04 LTS** (или 22.04, если 24.04 недоступен)
- Конфигурация: 2 vCPU / 4 ГБ RAM (лучше взять с запасом, чем ровно по минимуму)
- Регион — любой ближний к вам

Альтернативы, если хочется сравнить: Selectel, Beget Cloud, REG.RU Cloud VPS —
все работают по такому же принципу, шаги ниже не изменятся.

После создания сервера вы получите: **IP-адрес** и **root-пароль** (или SSH-ключ,
если провайдер предложит его сразу — тогда сохраните приватный ключ).

## Шаг 2. Купить домен и настроить DNS

Telegram Mini App **обязательно** требует HTTPS с настоящим доменом — просто
IP-адрес не подойдёт.

**Рекомендация: [REG.RU](https://www.reg.ru/)** — самый популярный
регистратор в РФ, `.ru`-домен стоит от ~200 руб/год (первый год часто дешевле).

1. Зарегистрируйте домен (например, `myteamflow.ru`).
2. В панели управления доменом найдите раздел **DNS-записи / Управление DNS**.
3. Добавьте (или отредактируйте) запись:
   - Тип: **A**
   - Имя/хост: `@` (это означает сам домен, без поддомена)
   - Значение: **IP-адрес вашего сервера из шага 1**
   - TTL: можно оставить по умолчанию
4. Подождите — DNS обновляется от нескольких минут до нескольких часов.
   Проверить, что домен уже смотрит на сервер, можно так (с вашего компьютера):

   ```
   ping myteamflow.ru
   ```

   Если в ответе виден IP вашего сервера — DNS настроен, можно идти дальше.
   Если старый IP или ошибка — подождите ещё и проверьте запись в панели.

## Шаг 3. Первое подключение к серверу

С вашего компьютера (PowerShell или обычный терминал):

```
ssh root@ВАШ_IP_АДРЕС
```

Введите пароль, который дал провайдер (или подключение пройдёт само, если
провайдер сразу настроил SSH-ключ). Дальше все команды в шагах 3–8 — это
команды **на сервере**, вводите их после подключения по SSH.

Создадим отдельного пользователя вместо работы под `root` (безопаснее):

```bash
adduser deploy
usermod -aG sudo deploy
```
(укажите пароль для нового пользователя, остальные поля можно пропустить
пустыми — Enter)

Дальше переключитесь на него и продолжайте все следующие шаги из-под него:

```bash
su - deploy
```

## Шаг 4. Установить Docker

Скопируйте и выполните на сервере (это официальный скрипт установки Docker):

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

После этой команды **выйдите и зайдите заново** по SSH (или наберите `exit`,
затем `ssh` и `su - deploy` снова) — иначе права на Docker не применятся.

Проверьте, что всё установилось:

```bash
docker --version
docker compose version
```

Должны напечататься версии без ошибок.

---

## Шаг 5. Настроить firewall

Разрешим только то, что нужно: SSH, HTTP, HTTPS.

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80
sudo ufw allow 443
sudo ufw --force enable
```

Проверить: `sudo ufw status` — должны быть разрешены 22, 80, 443.

## Шаг 6. Склонировать репозиторий на сервер

```bash
sudo mkdir -p /opt/sporthelper
sudo chown $USER:$USER /opt/sporthelper
git clone https://github.com/ВАШ_АККАУНТ/SportHelper.git /opt/sporthelper
cd /opt/sporthelper
```

(если репозиторий приватный — потребуется указать логин/токен GitHub при
клонировании, или настроить SSH-ключ для GitHub на сервере; проще всего —
на этом шаге временно сделать репозиторий публичным в настройках GitHub,
или создать [Personal Access Token](https://github.com/settings/tokens) и
использовать `https://ВАШ_ТОКЕН@github.com/...` в качестве URL для клонирования)

**Важно:** эта папка на сервере — только для деплоя. Никогда не редактируйте
в ней файлы руками — все изменения должны приходить через `git`
(вручную `git pull` или автоматически через GitHub Actions, шаг 10).

## Шаг 7. Создать `.env` на сервере

```bash
cp .env.production.example .env
nano .env
```

В открывшемся редакторе заполните (стрелки для навигации, `Ctrl+O` сохранить,
`Ctrl+X` выйти):

- `DOMAIN` — ваш домен из шага 2 (без `https://`, например `myteamflow.ru`)
- `POSTGRES_PASSWORD` — длинный случайный пароль (сгенерировать: наберите в
  терминале `openssl rand -hex 24` и скопируйте результат)
- `TELEGRAM_BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather).
  Если у вас уже есть бот из локальной разработки — **создайте новый,
  отдельный бот для продакшена** через BotFather (`/newbot`), не используйте
  токен от тестового бота.
- `TELEGRAM_BOT_USERNAME` — имя нового бота без `@`
- `MINI_APP_URL` — `https://` + ваш домен (например `https://myteamflow.ru`)
- `JWT_SECRET` — сгенерировать: `openssl rand -hex 32`
- `CORS_ORIGINS` — тот же `https://` + домен
- `YANDEX_DISK_OAUTH_TOKEN` и `YANDEX_API_KEY` — если хотите загрузку файлов
  и ИИ-функции сразу; можно оставить пустыми и добавить позже (приложение
  запустится и без них, просто эти функции будут отключены)

## Шаг 8. Первый запуск

```bash
docker compose up -d --build
```

Это займёт несколько минут (первая сборка образов). Проверьте, что все
контейнеры запустились:

```bash
docker compose ps
```

Должно быть 4 сервиса (`postgres`, `backend`, `bot`, `frontend`) со статусом
`running`/`healthy`. Если что-то не так — смотрите логи:

```bash
docker compose logs backend
docker compose logs bot
docker compose logs frontend
```

Проверьте, что backend отвечает:

```bash
curl https://ВАШ_ДОМЕН/api/health
```

Ожидаемый ответ: `{"status":"ok","database":true}`. Если ошибка про
сертификат — подождите минуту (Caddy запрашивает HTTPS-сертификат у Let's
Encrypt при первом запуске) и попробуйте снова.

Откройте `https://ВАШ_ДОМЕН` в браузере — должен открыться экран
«Откройте приложение через Telegram» (это нормально — Mini App работает
только внутри Telegram, см. следующий шаг).

## Шаг 9. Проверить бота в Telegram

Найдите вашего бота в Telegram по имени из `TELEGRAM_BOT_USERNAME` и
отправьте `/start`. Бот должен ответить и показать кнопку для открытия
Mini App — она откроет `MINI_APP_URL` внутри Telegram.

Если бот не отвечает — проверьте `docker compose logs bot` на сервере.

## Шаг 10. Настроить автодеплой через GitHub Actions

Сейчас обновления нужно делать руками (`git pull` + `docker compose up -d
--build` на сервере). Настроим, чтобы это происходило само при `git push`.

### 10.1. Сгенерировать отдельный SSH-ключ для деплоя

**На вашем компьютере** (не на сервере):

```
ssh-keygen -t ed25519 -C "github-deploy" -f github-deploy-key -N ""
```

Появятся два файла: `github-deploy-key` (приватный) и `github-deploy-key.pub`
(публичный).

### 10.2. Добавить публичный ключ на сервер

Содержимое `github-deploy-key.pub` добавьте на сервере в
`/home/deploy/.ssh/authorized_keys` (на новой строке):

```bash
# на сервере, под пользователем deploy
mkdir -p ~/.ssh
echo "СОДЕРЖИМОЕ_ФАЙЛА_github-deploy-key.pub" >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

### 10.3. Добавить секреты в GitHub

В репозитории на GitHub: **Settings → Secrets and variables → Actions →
New repository secret**. Создайте четыре секрета:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | IP-адрес вашего сервера |
| `DEPLOY_USER` | `deploy` |
| `DEPLOY_SSH_KEY` | всё содержимое файла `github-deploy-key` (приватный ключ, включая строки `-----BEGIN...-----`/`-----END...-----`) |
| `DEPLOY_PATH` | `/opt/sporthelper` |

После этого файл `github-deploy-key` на вашем компьютере можно удалить —
он сохранён в секрете GitHub.

### 10.4. Готово — проверка

Сделайте любое небольшое изменение локально, закоммитьте и запушьте в
`main`. Во вкладке **Actions** на GitHub увидите workflow `CI`: сначала
идут тесты (`backend-tests`, `frontend-build`), и если оба зелёные —
запускается `deploy`, который заходит на сервер и обновляет всё сам.

## База данных: как это работает, бэкапы и доступ

### Как она создаётся

Отдельно ничего настраивать не нужно — при первом запуске backend и бот
сами применяют схему (`database/schema.sql` + патчи из `database/patches/`)
к пустой базе. Данные лежат в Docker-volume `pgdata`, который **переживает**
`docker compose up -d --build`, `restart`, обновления через автодеплой —
то есть обычные обновления бота базу не трогают.

Единственная команда, которая **удалит** данные — `docker compose down -v`
(флаг `-v` стирает volumes). Обычный `docker compose down` (без `-v`) базу
не удаляет. Просто никогда не используйте `-v`, если не хотите специально
всё стереть.

### Бэкапы — обязательно настройте, это единственная копия ваших данных

Без бэкапов один сбой диска на сервере = потеря всех команд, профилей и
данных пользователей навсегда. Сделать дамп базы (замените `teamflow` на
значения `POSTGRES_USER`/`POSTGRES_DB` из вашего `.env`, если меняли их):

```bash
cd /opt/sporthelper
docker compose exec postgres pg_dump -U teamflow teamflow > /opt/backups/backup_$(date +%Y%m%d).sql
```

Сначала создайте папку под бэкапы: `mkdir -p /opt/backups`.

**Автоматизировать ежедневный бэкап** — добавьте задачу в cron:

```bash
crontab -e
```

Добавьте строку (бэкап каждый день в 3:00 ночи, храним только последние 7):

```
0 3 * * * cd /opt/sporthelper && docker compose exec -T postgres pg_dump -U teamflow teamflow > /opt/backups/backup_$(date +\%Y\%m\%d).sql && find /opt/backups -name 'backup_*.sql' -mtime +7 -delete
```

**Важно:** бэкапы на том же сервере не спасут, если сгорит весь диск
целиком. Периодически скачивайте свежий файл к себе на компьютер:

```bash
# с вашего компьютера
scp deploy@ВАШ_IP:/opt/backups/backup_20260101.sql .
```

или настройте автоматическую выгрузку куда-то ещё (например, на
Яндекс.Диск, который в проекте уже используется для файлов — простейший
вариант: `curl` с загрузкой дампа через Yandex.Disk REST API по расписанию;
для начала достаточно и ручного `scp` раз в неделю).

### Восстановление из бэкапа

```bash
cat backup_20260101.sql | docker compose exec -T postgres psql -U teamflow teamflow
```

### Ручной доступ к базе (для отладки)

Зайти в psql внутри контейнера:

```bash
docker compose exec postgres psql -U teamflow -d teamflow
```

Внутри — обычный SQL, например `\dt` покажет список таблиц, `\q` — выход.

## Как теперь обновлять бота (день за днём)

1. Меняете код локально, как обычно.
2. `git push` в `main` (напрямую или через Pull Request — как удобнее).
3. Всё остальное — автоматически: GitHub прогоняет тесты, и если они
   зелёные, сам заходит на сервер и обновляет контейнеры.
4. Проверить, что деплой прошёл — вкладка **Actions** на GitHub (зелёная
   галочка) или на сервере: `docker compose ps` / `docker compose logs -f`.

Если тесты красные — деплой просто не запустится, старая версия на сервере
продолжит работать как ни в чём не бывало.

## Диагностика проблем

- **Контейнер постоянно перезапускается**: `docker compose logs <имя>` —
  почти всегда причина видна в последних строках (неверный `.env`, не
  запустился Postgres и т.п.).
- **Сертификат HTTPS не выдаётся**: убедитесь, что DNS (шаг 2) уже
  указывает на сервер, и что порты 80/443 открыты (шаг 5) — Let's Encrypt
  должен достучаться до сервера снаружи, иначе Caddy не сможет подтвердить
  домен.
- **Бот не отвечает, но `docker compose ps` показывает `running`**:
  проверьте `TELEGRAM_BOT_TOKEN` в `.env` — если он неверный или это токен
  другого бота, `docker compose logs bot` покажет ошибку авторизации.
- **Откатить на предыдущую версию**: на сервере,
  `git log --oneline -5` — найти нужный коммит, затем
  `git reset --hard <хеш>` и `docker compose up -d --build`.
- **Полностью пересобрать с нуля** (например, после чистки диска):
  `docker compose down && docker compose up -d --build`. База данных в
  Postgres сохранится (она в отдельном docker-volume) — теряются только
  сами контейнеры, не данные.
