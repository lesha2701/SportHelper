# Автоматические выплаты тренерам (задача #39)

> Статус: **этап 1 реализован, выключен по умолчанию**. Работает на имитации банка (`PAYOUT_PROVIDER=fake`, только для разработки);
> реальный провайдер подключается этапом 2, когда банк / ЮKassa подтвердят условия (см. «Что нужно выяснить»). Реальных денег
> при разработке не использовалось. Ручной процесс ([finance.md](finance.md), раздел про выводы) остаётся рабочим и основным,
> пока автоматика выключена.

## Принципы

1. **Выплачивается ровно зарезервированная сумма.** Сумма попытки берётся из заявки, а не из чьего-то ввода; БД сама отказывает
   в попытке с другой суммой (триггер) и во второй «живой» попытке по той же заявке (уникальный индекс).
2. **Ключ идемпотентности у провайдера = id заявки** (`withdrawal:<id>`). Одна заявка не может стать двумя операциями.
3. **Провайдера вызываем вне транзакции.** Деньги в книге меняются только охраняемым переходом статуса: успех → `paid` (+ запись
   в журнале), **доказанный отказ** → `rejected` (+ снятие резерва), всё остальное остаётся `processing` для человека.
4. **Сбой вызова никогда не повторяется системой.** Операцию ищем у провайдера по ключу; если ответа нет, ждёт человек, деньги сами
   не возвращаются (иначе можно выплатить дважды).
5. **Сумма в ответе провайдера сверяется с нашей.** Расхождение останавливает автоматику.
6. **Любая неожиданность останавливает автоматику** (`payout_automation_state`), пока финансовый администратор не возобновит её
   (`POST /api/admin/finance/payouts/automation/resume`, нужен свежий второй фактор, пишется в журнал аудита). Остановка не трогает
   деньги, которые уже в пути: их доводит до конца сверка по ключу.

## Когда заявку НЕ платит система (остаётся человеку, причина в `attention`)

| Правило | Настройка |
|---|---|
| сумма выше лимита автовыплаты | `PAYOUT_AUTO_MAX_RUB` (5000) |
| суточный лимит на тренера / на всю платформу | `PAYOUT_AUTO_DAILY_TRAINER_RUB` (15000) / `PAYOUT_AUTO_DAILY_TOTAL_RUB` (300000) |
| **первая выплата** тренеру (всегда вручную) | — |
| реквизиты, на которые тренеру ещё не платили, моложе паузы | `PAYOUT_NEW_DETAILS_COOLDOWN_HOURS` (72) |
| те же реквизиты есть у другого тренера | — |
| получатель не совпадает с именем и фамилией из профиля | — |
| пароль менялся недавно (та же пауза) | `PAYOUT_NEW_DETAILS_COOLDOWN_HOURS` |
| за тренером долг, есть замороженные начисления (спор), аккаунт заблокирован/удаляется | — |
| резерв в книге меньше заявки | — |

Перед вмешательством системы у тренера есть пауза на отмену: `PAYOUT_AUTO_DELAY_MINUTES` (10). Создание заявки по-прежнему требует
пароль, ограничено по частоте и идемпотентно (`client_key`).

## Остановка автоматики (рубильник)

Вручную: `PAYOUTS_AUTO_ENABLED=false`. Сама система останавливается при: нет ответа банка; банк назвал другую сумму; ответ банка по
заявке не в статусе `processing`; не удалось записать выплату; не прочитаны реквизиты; **3 отказа банка за час**; **расхождение со
сверкой**. Всем финансовым администраторам уходит уведомление; на сайте/в админке видно причину (`GET /payouts/automation`).

## Сверка

Раз в час выписка провайдера за 26 часов сверяется с `payout_attempts`: операция есть у банка и неизвестна нам, суммы, статусы
(проведено у нас ↔ у банка). Любое расхождение останавливает автоматику.

## Админские действия при автоматических выплатах

- Пока перевод `created/sent/succeeded` (в пути), админ не может ни отклонить, ни провести его вручную (`409 payout_in_flight`).
- Перевод без ответа (`unknown`): админ смотрит кабинет банка и либо отклоняет заявку («деньги не отправлены», попытка → `failed`,
  резерв возвращается), либо проводит вручную с банковским идентификатором (попытка → `succeeded`).

## Конфигурация

`PAYOUT_PROVIDER` (`manual` | `fake`), `PAYOUTS_AUTO_ENABLED`, `PAYOUT_AUTO_DELAY_MINUTES`, `PAYOUT_AUTO_MAX_RUB`,
`PAYOUT_AUTO_DAILY_TRAINER_RUB`, `PAYOUT_AUTO_DAILY_TOTAL_RUB`, `PAYOUT_NEW_DETAILS_COOLDOWN_HOURS`,
`PAYOUT_UNKNOWN_ESCALATE_MINUTES`, `PAYOUT_BATCH`. Запуск в `APP_MODE=main` запрещён с `PAYOUT_PROVIDER=fake`, а также с
`PAYOUTS_AUTO_ENABLED=true` без провайдера или без `FINANCE_ADMIN_EMAILS`.

## Этап 2: что нужно выяснить, прежде чем подключать реальный провайдер

Делает владелец (письма в банк / ЮKassa), технически провайдер подключается через интерфейс `PayoutProvider`
(`backend/app/integrations/payouts.py`): `send` (идемпотентно по ключу), `status` (по ключу), `statement`.

1. **ЮKassa:** разрешены ли нам выплаты физлицам/самозанятым; **откуда берутся деньги** (баланс ЮKassa или пополнение платёжкой с
   расчётного счёта в Альфа-Банке; ЮKassa сама деньги с нашего счёта не списывает); комиссия, лимиты, сроки, тестовая среда.
2. **Альфа-Банк (если выплаты напрямую):** есть ли в Alfa API исходящие выплаты физлицам / СБП; можно ли проводить платёж **без
   подписи человека** (по документации API создаётся черновик, подписывается в «Альфа-Бизнесе»); лимиты, IP-ограничения, песочница.
3. **Налоги и чеки:** статус тренеров (самозанятые, чек «Мой налог»), выплаты не самозанятым (НДФЛ, взносы), модель «агент / продавец»
   ([finance.md](finance.md), вопросы F5, 6–7).
4. Ключи провайдера хранятся только в серверном `.env`, отдельная роль с минимальными правами, привязка к IP сервера, суточный лимит
   на стороне банка.
