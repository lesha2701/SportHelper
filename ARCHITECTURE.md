# Архитектура SportArenaGlobal: кто с кем разговаривает и кто за что отвечает

Документ короткий и рабочий: по нему мы решаем, куда класть логику, в каком порядке делать фичу и что нельзя ломать.
Подробности по темам лежат в `docs/` (авторизация — `docs/auth.md`, деплой — `docs/deployment.md`, мобильный вход — `docs/mobile.md`,
iOS — `docs/ios/`).

## 1. Схема

```
  iPhone-приложение      Android-приложение        Сайт
  (SwiftUI)              (React Native + Expo)     (React + Vite)
        \                       |                    /
         \                      |                   /
          ───────────  HTTPS, один API: /api  ───────────
                                |
                      Бэкенд (FastAPI, Python 3.12)
                      вся логика, права, расчёты, ИИ, уведомления
                                |
                  PostgreSQL        файлы (Яндекс.Диск)
```

Всё, кроме клиентов, живёт на одном сервере (`/opt/sporthelper`, Docker Compose, перед ним Caddy). Сайт отдаётся с того же сервера,
что и API.

## 2. Главные правила

1. **Бэкенд — единственный источник правды.** Права доступа, бизнес-правила («кто может удалить матч», «сколько турниров у команды»),
   расчёт статистики, уведомления, ИИ и работа с файлами живут только на сервере. Проверки на клиенте нужны для удобства человека, а не
   для безопасности: любой запрос можно отправить в обход приложения.
2. **Клиенты общаются с сервером только через API.** Ни один клиент не знает про устройство БД и не получает «особых» данных мимо API.
3. **Сайт — такой же клиент, как приложения.** Если эндпоинт нужен нескольким клиентам, он общий. Эндпоинты «только для веба» заводим
   лишь для админки.
4. **Клиент не должен ломаться, если сервер старее или новее.** Подробности в разделе 5.
5. **Сначала сервер, потом клиенты.** Клиентская фича, которой нет на сервере, не выкатывается.

## 3. Из чего состоит проект и кто владелец

| Часть | Где лежит | Стек | Владелец |
|---|---|---|---|
| Бэкенд + БД | `backend/`, `database/` (репозиторий `SportHelper`, ветка `main`) | FastAPI, asyncpg, PostgreSQL, SQL-патчи `database/patches/NNNN_*.sql` | оба вместе |
| Сайт | `frontend/` (там же) | React 19, TypeScript, Vite, CSS-модули | оба вместе |
| Android-приложение | папка `mobile/` в `main` репозитория `SportHelper` | React Native, Expo, Expo Router, TypeScript | разработчик Android |
| iPhone-приложение | папка `ios/` в `main` репозитория `SportHelper` (бывший репозиторий `SportArenaIOS`, заархивирован) | SwiftUI (iOS 17+), пакет `SportArenaKit` с моделями и сервисами | разработчик iOS |

Оба разработчика работают вместе с ИИ-помощником. От этого правила не меняются: **ответственность за часть несёт человек, а не
помощник.** Человек читает результат, запускает тесты и принимает изменение.

Что значит «владелец»:
- решает, как устроен его клиент, и сам выпускает его в App Store / Google Play;
- следит за тем, чтобы клиент не ломался после изменений сервера;
- вправе потребовать от бэкенда изменения контракта (но не вносит его молча: см. раздел 4).

Что значит «оба вместе» для бэкенда, БД и сайта:
- любое изменение идёт запросом на слияние (pull request) и видно в нём, в том числе дифф контракта `docs/openapi.json`; в `main` его сливает владелец
  репозитория (iOS-разработчик), второй разработчик присылает свою часть запросом;
- слияние в `main` и есть деплой: CI после тестов сам выкатывает сервер и сайт на прод. Поэтому миграцию и ломающее изменение сливают
  осознанно, и только когда клиенты к этому готовы (раздел 5, порядок выкатки).

## 4. Контракт API

Контракт — это **договорённость между сервером и тремя клиентами**. Сейчас он описан в нескольких местах, и это главная причина путаницы:

| Что | Где сейчас |
|---|---|
| **Контракт API (источник правды)** | `docs/openapi.json` — выгружается из приложения; для приложений без админских маршрутов `docs/ios/openapi-mobile.json` (тоже выгружается) |
| Описание для iPhone (задание, примеры) | `docs/ios/README.md` |
| Описание для Android (вход по токену) | `docs/mobile.md` |
| Общее: вход, сессии, безопасность | `docs/auth.md` |
| Swagger / `openapi.json` самого сервера | `/docs`, но на проде выключен (`API_DOCS_ENABLED`) |

**Как это работает (с 10.11.2026).** Контракт не пишется руками: `python scripts/export_openapi.py` (из папки `backend/`) строит его из самих
маршрутов FastAPI и записывает `docs/openapi.json` (всё) и `docs/ios/openapi-mobile.json` (без админских маршрутов, их приложения не вызывают).
Тест `tests/test_openapi_contract.py` падает, если файлы устарели, поэтому любое изменение эндпоинта, поля или ошибки обязательно видно в том же
запросе на слияние как дифф `docs/openapi.json`, и второй разработчик тоже его видит. Правило: изменили API → выгрузили контракт → закоммитили.

### Авторизация (сейчас две схемы)

| Клиент | Как входит | Как шлёт запросы |
|---|---|---|
| Сайт | `POST /api/auth/login`, сессия в HttpOnly-cookie | cookie и заголовок `X-CSRF-Token` на изменяющих запросах |
| iPhone | то же самое, cookie + CSRF | `URLSession` с общим хранилищем cookie |
| Android | `POST /api/auth/mobile/login` (включается `MOBILE_AUTH_ENABLED=true`), в ответе токен | `Authorization: Bearer <токен>`, токен лежит в `expo-secure-store`, CSRF не нужен |

Обе схемы работают на одной таблице сессий и одинаково отзываются (`/api/auth/logout`, список сессий в аккаунте). Это нормальное
состояние, но его надо держать осознанно:
- **Решение, которое нужно принять:** оставить две схемы или перевести iPhone тоже на токен. Я бы оставил как есть, пока не появится
  причина менять: cookie для iPhone уже работает и проверена тестами. Если Apple или будущие push-уведомления потребуют токен, перейдём.
- Любое изменение входа (2FA, смена пароля, подтверждение почты) проверяется на **всех трёх** путях входа.

### Формат (общий для всех)

JSON, `snake_case`, идентификаторы UUID, даты ISO 8601 (время броней в UTC), деньги в финансовых методах — целые копейки, ошибки в
едином виде `error.code/message/field`, лимиты файлов: фото до 10 МБ, видео до 100 МБ и 60 секунд. Подробности — `docs/ios/README.md`,
раздел «Формат».

## 5. Совместимость: что нельзя ломать

Старые версии приложений живут у людей неделями и месяцами, а выпуск в магазины занимает дни. Поэтому:

1. **Меняем только добавлением.** Новые поля и эндпоинты — можно. Переименовать, удалить поле, сменить тип, сделать необязательное
   обязательным — нельзя без новой версии API.
2. **Запросы без нового поля ничего в нём не меняют.** Так сделаны `tournaments` и `home_venue` команды: если поля нет в запросе,
   значение сохраняется, пустое значение очищает. Иначе старое приложение при сохранении команды сотрёт то, чего не видело.
3. **Клиент терпит отсутствие поля в ответе.** Старый сервер или ответ без поля не должен ронять экран (см. `Team.tournamentList` в iOS).
4. **Порядок выкатки:** миграция → бэкенд → клиенты. Миграция не должна ломать старый код бэкенда (добавление столбцов с значением по
   умолчанию — безопасно, удаление и переименование — нет).
5. **Настоящее ломающее изменение** — только через `/api/v2` или через «минимальную поддерживаемую версию клиента» (сервер сообщает
   её, приложение просит обновиться). Пока этого механизма нет; его нужно завести до первого такого случая.

## 6. Как делается фича (одинаково для всех)

1. **Описание.** Что нужно, кто видит (игрок, тренер, администратор), какие права. Одна страница, лежит в запросе на слияние.
2. **Контракт.** Какие эндпоинты и поля, какие ошибки. Если фича меняет что-то существующее, отдельно написано, как это переживут
   старые клиенты (раздел 5).
3. **Бэкенд:** миграция, репозиторий, схемы, роуты, тесты (`backend/tests`). Слияние в `main` — после зелёных тестов запроса.
4. **Деплой сервера.** Происходит сам при слиянии в `main` (раздел 8): слейте, когда готовы к выкатке.
5. **Клиенты** работают параллельно по контракту: сайт, iPhone, Android. Каждый ведёт свою строку в таблице соответствия (раздел 9).
6. **Проверка:** тесты своего слоя и живой прогон против настоящего локального сервера (у iPhone UI-тесты ходят в настоящий
   локальный бэкенд, а не в заглушку).

Что не делается: фича целиком в клиенте, которой «пока нет» на сервере; «временное» правило прав в приложении вместо сервера.

## 7. Где держать код: один репозиторий или несколько

Код лежит в одном репозитории: бэкенд, сайт, Android (`mobile/`) и iPhone (`ios/`) в `SportHelper/main`. iPhone перенесён из
`SportArenaIOS` с историей (`git subtree add`), старый репозиторий заархивирован.
Андроид-ветка `feature/mobile-app` влита в `main` 10.11.2026 (запросы №1 и №2), дальше работаем короткими ветками от `main`.
Что это даёт: изменение бэкенда можно сопроводить правкой всех клиентов одним запросом, а контракт лежит в одном месте
(`docs/ios/` для iPhone, `docs/mobile.md` для Android; общий `openapi.json` — следующий шаг).

**Рекомендация.** Один репозиторий, но не ветки: каждая платформа — **папка в `main`**.

```
SportHelper/            (репозиторий)
  backend/   database/   frontend/        общее: сервер, БД, сайт
  mobile/    (или android/)               Android
  ios/                                    iPhone (SportArenaKit + App + UI-тесты)
  docs/      ARCHITECTURE.md              контракт, архитектура, описания
```

Почему не ветка `feature/ios`: ветка с платформой неизбежно расходится с `main` (мы это уже видим на Android), правки бэкенда в ней
теряются, а «текущая версия» перестаёт быть единой. Короткие ветки для отдельных фич — нормально, долгая ветка на всю платформу — нет.

Что для этого нужно (в таком порядке, ничего не делается автоматически):
1. ~~Влить `feature/mobile-app` в `main`~~ — сделано 10.11.2026 (бэкенд-часть отдельным запросом №1, затем `mobile/` запросом №2). Осталось на проде включить `MOBILE_AUTH_ENABLED=true` (вместе с деплоем, по решению о деплое).
2. ~~Перенести iPhone в папку `ios/`~~ — сделано (запрос из ветки `feat/ios-into-repo`): история сохранена (`git log` по репозиторию видит старые коммиты,
   но `git log -- ios/…` показывает только коммит переноса; старые смотрим в архиве `SportArenaIOS`), `.gitignore` внутри `ios/`.
3. ~~Добавить `CODEOWNERS`~~ — сделано: `mobile/` — разработчик Android, всё остальное (в том числе `ios/`, `backend/`, `frontend/`, `docs/`) — владелец репозитория.
4. ~~Фильтры по путям~~ — сделано частично: правка только `ios/`, `mobile/` или текстовых документов не запускает тесты сервера и сайта и не выкатывает прод;
   тесты запускаются один раз на запрос и один раз на `main` (а не на каждую ветку).
   Тесты iPhone и Android пока запускаются локально (нужен macOS-раннер для iOS, это отдельное решение).

Что остаётся неудобным в одном репозитории (решение принято 10.11.2026): размер, разные цепочки сборки, посторонние коммиты в общей истории. Это решается
фильтрами по путям и дисциплиной коммитов (`feat(ios): …`, `feat(mobile): …`, `feat(web): …`, `feat(api): …`). Если команда
решит, что цена слишком высока, вариант «iPhone остаётся отдельным репозиторием» тоже работает, но тогда контракт обязательно живёт
**только** в `SportHelper/docs/`, а iOS берёт его оттуда.

## 8. Окружения и выпуск

| Окружение | Для чего | Как поднимается |
|---|---|---|
| Локальное | разработка и UI-тесты | свой PostgreSQL и свой бэкенд, тестовые учётки, порт 8010 |
| Прод | живые пользователи | сервер `/opt/sporthelper`, Docker Compose, миграции применяются при старте бэкенда |

Нет промежуточного окружения («staging»): всё, что мы проверяем перед прод, проверяем на локальном. Для серьёзных изменений БД
(например, массовая миграция) стоит завести копию прод-БД без персональных данных и прогонять на ней.

Правила выпуска:
- **Деплой на сервер — слияние в `main`.** CI запускает тесты, и только если они зелёные, по SSH обновляет `/opt/sporthelper` (`git reset --hard origin/main`,
  `docker compose build`, `up -d`). Порядок: миграция → бэкенд → сайт, всё это делается одним проходом. Приложения выпускаются после.
  Правки только в `ios/`, `mobile/`, текстовых документах (`*.md`) и `.github/CODEOWNERS` ни тестов, ни выкатки не запускают. Откат — «Revert» запроса в GitHub
  (или `git reset --hard <коммит>` на сервере, но следующее слияние снова выкатит `main`). Файл `.env` на сервере деплой не трогает.
- Сайт и бэкенд едут на сервер вместе; приложения живут своей жизнью (магазины).
- Перед выкладкой приложения проверяем, что нужная миграция и ручки уже на проде.
- Секреты (ключи, пароли, токены) не лежат в репозитории и не пересылаются в чатах. Пароль из реального окружения, оказавшийся в
  переписке, считается скомпрометированным: его меняют.
